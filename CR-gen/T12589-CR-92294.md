### Issue Description
```
h4. +Description:+
Found by AWPTCM-T12589 "Interoperability with RIPv1/v2 (Policy Based Routing)" on a 3-member IE520-28GSX VCStack, awplus_main-20260923-20.

A policy route (mls qos + hardware ACL class-map + {{set ip next-hop}}) on the ingress port sends matching traffic to its next hop correctly while that next hop is reachable and already in the ARP table.

*Expected:* when the next hop is not usable, matched traffic falls back to the routing table (here a RIP route), as the test case states.
*Actual:* the DUT neither falls back nor drops. Every matched packet is routed back out of the *ingress port, untagged in vlan1, to the MAC of an unrelated host* (10.38.215.1, a host on the native VLAN of the ingress trunk). Seen for every form of unusable next hop tried, under RIPv2 and RIPv1 alike:
* next-hop VLAN shut ({{shutdown}} on interface vlan3230)
* next hop in a connected subnet but no host there ({{set ip next-hop 172.16.30.99}})
* next hop with no route ({{set ip next-hop 10.99.99.1}}; accepted with no error)

The packets are routed, not bridged: source MAC = the stack's router MAC, destination MAC = the ARP entry of 10.38.215.1, egress untagged on port3.0.10 although they arrived tagged in vlan3210. With next hop 172.16.30.99 or 10.99.99.1, the valid 172.16.30.2 was in the ARP table and was not used.

Also: PBR never resolves its own next hop. After {{no shutdown}} on the next-hop VLAN (which removes the 172.16.30.2 ARP entry), matched traffic is still misrouted as above and does not re-create the entry. PBR works again only once something else makes the DUT ARP the next hop (here {{ping 172.16.30.2}} from the DUT).

Traffic not matching the policy was routed correctly by RIP in every run. RIPv1 and RIPv2 both work between the stack, a standalone IE520 and an x230; the RIP version makes no difference.

Not separated by the data: in every run 10.38.215.1 was at once the first (lowest-addressed) entry in {{show arp}}, the only entry learned on the ingress port, and the only entry in vlan1.

Network impact: matched flows are lost to their destination and delivered to a different host in a different VLAN, silently (no error, log or counter). On the test bench the receiving host forwarded them on, so spoofed-source traffic left the lab until a firewall rule was added.

h4. +Consequences:+
Lose traffic / unexpected traffic flow: all policy-matched traffic is delivered to an unrelated host in another VLAN for as long as the next hop is down, unresolved or unroutable. It does not recover by itself when the next hop comes back: the misrouting continues until the next hop's ARP entry is created by other means (a ping from the DUT, or other traffic to that address). No reboot is needed.

h4. +Reproduction Method:+
Topology and configuration as in Network Configuration and Device Configuration.
# On the DUT, have at least one other host in the ARP table (here 10.38.215.1 in vlan1, on the ingress port).
# Send traffic into port3.0.10, tagged vlan3210, from 192.168.10.1-254 to 172.16.89.2. Sources .128-.254 match the policy.
# With the next hop up and resolved: matched traffic goes to vlan3230 (x230), unmatched to vlan3240 (RIP route). Correct.
# {{interface vlan3230}} / {{shutdown}}, send again. Matched traffic leaves port3.0.10 untagged to the MAC of 10.38.215.1 (expected: vlan3240).
# {{no shutdown}}, send again. Still misrouted; {{show arp}} has no 172.16.30.2. {{ping 172.16.30.2}} from the DUT, send again: correct.
# {{set ip next-hop 172.16.30.99}} and then {{set ip next-hop 10.99.99.1}}, send each time. Misrouted as in step 4.
# {{router rip}} / {{version 1}} on all three switches and repeat 3-6. Same results.
```
