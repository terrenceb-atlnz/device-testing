During the SVT System Startup test (1000 power-cycles, 1000 reboots) on the IE520-28GSX PT1, an issue was observed.

Power-cycling recovers the DUT.

It does not appear that any debug or crash files were generated.

The issue was not observed after the DUT was power-cycled 1000 times.

The test has been restarted.

UPDATE (21 October 2026):

The issue was reproduced running the following bootloader/software:
Bootloader version : 9.2.0

Summary

CR-92097 appears to involve an intermittent lockup of an IE520-28GSX after a software reboot during SVT startup testing. The DUT may become powered but unresponsive, with no console output after the bootloader/kernel handoff and no crash or debug file generated. The issue may affect reboot reliability and, in one reproduction, was accompanied by an apparent reset of the running configuration to defaults.

Probable Root Cause Analysis

This likely stems from an incomplete hardware reset sequence during software reboot on the IE520 platform. A probable contributing cause is the gpio-restart driver failing to probe, as indicated by the kernel messages in E6 and the driver/pinmux explanation in E7. If the reset GPIO is not correctly configured or asserted, the SoC may remain powered but fail to complete boot, which is consistent with the no-output lockup in E2 and E5 and the power-cycle recovery in E1.

The reproduction on a build believed to contain the gpio-restart fix (E8, E9, E10) suggests that the probe failure may be only one contributing factor, or that the fix may not fully address the underlying reset/pinmux behaviour. The separate observation of configuration reset to defaults on the 164th reboot (E4) may indicate a secondary issue in the reboot shutdown path, filesystem flush, UBI/UBIFS persistence, or default-config fallback. The absence of crash/debug files (E1) suggests the failure may occur before normal crash handling is available, or in a state where the system cannot write diagnostic data.

The evidence suggests a reboot-path failure rather than a simple software crash. E2 and E5 show that the system reaches the bootloader/kernel handoff but then produces no further console output, while E1 indicates the SoC remains powered and only recovers after power-cycle. E6 and E7 point to a concrete gpio-restart probe failure with error -524, which may prevent the reset GPIO from being configured or asserted correctly. If the reset line is not driven as expected, the SoC may be left in a powered but non-functional state. Analysis of problem:

Gpio-restart driver (not cause of problem, but still not good to fix)

The gpio-restart driver which is responsible for resetting the hardware on software reboot was failing to probe.

It fails to probe because the driver fails to configure the gpio as an input, and the pinmux configuration only allows the pin to be an output (despite the hardware being capable).

i2c bus lockup (cause)

If a software reset occurs while an i2c device is part way through a
transfer, it can keep driving SDA low.

On the IE520GSX, SDA is shared between all i2c devices, however sclk goes through a demultiplexer such that each SFP can be individually selected and if not selected, the SFP is isolated from SCL.

This configuration means that normal I2C bus recovery which the kernel
will try to perform on boot, doesn't work as the SCL pulses won't reach
the module locking the bus unless its SCL channel is selected.

Additional flash unmounting problem

On software reboot, shutdown.c unmounts filesystems straight after sending SIGKILL to all processes. A killed process releases its files only when it finishes exiting, so umount("/flash") can fail with EBUSY. The failure is ignored, the device reboots with /flash mounted, and UBIFS needs recovery on the next boot

Code Change Description:

Gpio-restart driver (not cause of problem, but still not good to fix){}

Remove the open-source flag from the relevant node in the DT, such that the driver requests the gpio as an output and actively drives the pin high until reset.

i2c bus lockup (cause)

Add a routine to the bootloader which if the bus is found locked (SDA low) will clock each SFP channel until SDA is released.

Additional flash fix to possibly help with flash problem seen during testing

On software reboot, retry un-mounting the filesystem if it didn't work
