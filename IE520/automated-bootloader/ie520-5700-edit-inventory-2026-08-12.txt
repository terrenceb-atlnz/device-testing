PART A - IE520 OUTPUT DIVERGENCES (5 defects) - PRODUCT QUESTIONS
================================================================================
These are NOT test bugs. The test string is live on other platforms. The IE520
emits something different. Each gate below was widened or replaced so the IE520
would pass; that masks a product-side difference and should be escalated, not
ported.

Each entry gives the TRIGGER (the operator action that reproduces it), WHERE IT
FIRES (suite and case), and OCCURRENCES across the whole campaign on both
platforms.

A0  PROBABLE COMMON ROOT CAUSE - THE IE520 IS RUNNING MAINLINE U-BOOT
--------------------------------------------------------------------------------
    D1 through D5 are very likely NOT five findings. They are one, observed at
    five different places.

    BOOTLOADER BANNERS, device output, whole campaign:

      x230v2    "Bootloader 6.2.37 loaded" .................. 432
                any U-Boot banner ............................. 0

      IE520     "U-Boot 2025.01-04843-g6eaac4e1fcad" ........ 883
                "U-Boot 2025.01-04844-gd2292467da4d" ........ 112
                "U-Boot 2025.01" (total) .................... 995
                "Bootloader 9.1.0 loaded" ................... 112

    x230v2 NEVER shows a U-Boot banner. The IE520 shows one 995 times, against
    only 112 showings of the AT bootloader banner.

    SUPPORTING STRING - U-Boot's own environment-save output:

      "Saving Environment to SPIFlash"    x230v2 = 0     IE520 = 142

    Zero occurrences on x230v2 in any suite. That string is verbatim mainline
    U-Boot env_save() output from the SPI-flash environment driver, and it is
    what splits D3 and D4.

    INFERENCE (strongly supported by the above; NOT proven from source):
      The IE520 runs mainline U-Boot 2025.01 with a thin Allied Telesis
      bootloader layer over it that does not suppress U-Boot's console output.
      x230v2's Bootloader 6.2.37 fully wraps U-Boot and never leaks it.

    If that holds, every entry below is the same leak seen at a different point:
      D1  FIT loader output instead of the AT release-verification line
      D2  U-Boot's filesystem listing ahead of the AT selection menu
      D3  U-Boot env_save() progress inside an AT message pair
      D4  U-Boot env_save() progress inside an AT message pair
      D5  U-Boot FIT config-node lookup instead of the AT platform check

    THE QUESTION FOR THE BOOTLOADER TEAM IS THEREFORE SINGULAR:
      "Is the IE520 intended to run mainline U-Boot with a reduced AT bootloader
       layer, and if so, is the leaked U-Boot console output intended?"
    Everything in Part A follows from the answer.

      TWO SIDE EFFECTS OF OPTION 7 WORTH KNOWING (both observed, neither is a
      defect, but both will break automation that does not expect them):

      (a) IT REVERTS THE CONSOLE BAUD RATE and tells you so, then WAITS for you
          to follow it down before continuing. 9600 is the factory default; a
          non-default rate is a stored setting (Boot Menu option 4, "Adjust the
          console baud rate"). Anything driving the console must reopen the port
          at 9600 and send ENTER, or the boot appears to hang.

      (b) IT CLEARS THE STORED NETWORK SETTINGS. The one-off-boot TFTP dialogue
          loses its defaults:
              before option 7:  ... to download from (eth0-eth0) [eth0]:
              after  option 7:  ... to download from (eth0-eth0) []:
          With an empty default a bare ENTER no longer accepts anything - it
          ABORTS back to the device menu. Scripts that "Enter through" those
          prompts will silently fall out of the dialogue on any unit that has
          had a factory restore, which is exactly the state 2005 cases 2 and 3
          leave behind.

PART D - METHOD, AND A TRAP THAT PRODUCES FALSE CONCLUSIONS
================================================================================
HOW TO CLASSIFY A FAILING GATE
  1. grep -a the string in the CONTROL platform's console logs
     (raw-data/test_scripts/5700_bootloader/swi_a_2*.log)
  2. Live there -> IE520 DIVERGENCE. Escalate. Do not widen the gate.
  3. Absent there too -> genuine rot, and fixing it is correct.
  4. Filter framework echoes either way: drop lines matching
     ^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}:
     The framework logs its own strList, so without this filter you match OUR
     text and conclude the device emits a string it never printed.

*** grep READS THESE CONSOLE LOGS AS BINARY ***
  swi_a_*.log on BOTH platforms contain control bytes. Plain grep prints nothing
  and grep -c returns 0 - INDISTINGUISHABLE FROM A REAL ABSENCE. Always use
  grep -a. During this analysis that produced a false "0 occurrences on both
  platforms" for five separate strings before it was caught.

NEVER call a gate "rot" from one platform's logs alone. Doing so converts a
product finding into a test change.

CONSOLE READS SPLIT STRINGS MID-TOKEN
  The read buffer chunks arbitrarily - "... sha1<EOS>" in one read, "+ OK" in
  the next - so matching a full literal is a coin flip even when the string IS
  correct. Gate on short atomic markers, and always pass an explicit waitTime.

VERIFY A REPLACEMENT GATE AGAINST ORDERING, NOT JUST PRESENCE
  See B1: anchoring on a string the device prints two lines EARLIER truncates the
  output before the line the assertion needs, converting a slow pass into a
  failure.

  belongs in their teardown - a menu selection is not enough. The same applies to
  any case that clears a security level.
