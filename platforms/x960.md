# x960 — platform facts (AT-x960-56YSQ and AT-x960-28YSQ)

**What this is.** The platform, firmware and CLI behaviour of the x960 family that has cost
hardware hours, been mistaken for a defect, or would otherwise be re-derived. Read it whenever
the DUT's family is x960 (`/orient-dt` §2). Unless a row says otherwise, everything measured
here was measured on **tb277**, on the build it names. What any bench *currently* is (cabling,
boot source today, which ports are cabled) is never written here: that is the box's generated

## 1. 🔥 The two models do NOT share a switching core

This is the single most load-bearing fact about the family, and it is invisible from the CLI.

| model | switch chip | family | note |
| --- | --- | --- | --- |
| **x960-56YSQ** | **Marvell 98CX8514** | **Falcon** | **no PHYs** — every port connects directly to the switch chip |
| x960-28YSQ | Marvell 98DX4580M | AlleyCat5P-XL | has MACsec support |

Source: TPS. The CPU on both is a Marvell CN9130 (Octeon family) multi-core ARMv8.

**Consequence, and the Test Strategy says it in as many words:** *"The Falcon switching core is
new to this family. Results from the x960-28YSQ demonstrate nothing about this board's
dataplane"* and *"ART on another platform proves nothing about this"*. So:

- A dataplane result from the -28 is **not** evidence about the -56, even though both report the
  same software version and the same `show` output.
- ART/CR history from other platforms (the `1336_acl` suite's CRs were raised on FS980 and
  GS970EMX) points at *where to look*, never at what this board does.
- There is **no reference platform** for Falcon in this project. The Test Strategy's instruction
  is to verify dataplane behaviour from first principles against the TPS limits.

Related: [[corpus-sources-are-not-authoritative]].

## 2. Falcon TCAM — the limit behind most "odd" ACL/QoS behaviour

From the TPS. The TCAM is shared between QoS, ACLs, tunnel terminations and subnet-based VLANs.

| | AC5P-XL (the -28) | **Falcon (the -56)** |
| --- | --- | --- |
| raw | 24K x 20-byte rules | 36K x 10-byte = 18K x 20-byte, **split over two control pipes** |
| usable 20-byte rules | 24K | **9K** |
| ACLs (60-byte rules) | 8K with an AC5P-XL-only silicon profile | **3K max**, if nothing else used the TCAM |

**The project works to a 2.5K 60-byte rule budget**, chosen as the lowest common denominator so
mixed stacking works. The Test Strategy lists *"TCAM consumption against the chosen 2.5K rule
budget on Falcon"* as a named risk, and calls out *"TCAM utilisation and contention with QoS"* as
a coverage area.

- **Check it with `show platform classifier statistics utilization brief`** (ACL guide p18).
- When an ACL is accepted but does not take effect, or a QoS policy displaces one, suspect TCAM
  exhaustion before suspecting the feature. The two-pipe split is its own hazard: rules are not
  one flat pool.

## 3. MACsec and flow control are NOT supported on the -56

- **MACsec: not supported on the x960-56YSQ** — the Falcon chip does not have it (TPS). On the
  **-28** it is supported, but **not on ports 17–24** (silicon: MACsec covers only the first two
  DMA groups, lanes 0–15), and on ports 25/29/33/37 it is handled by the 100G uplink PHY and
  works only from 5.5.6-2 onward.
- **Flow Control: `No` — *"Cannot be supported due to a silicon issue"*** (TPS row 155).
  This is what a real platform limit looks like in the TPS, and it is the evidence an
  UNSUPPORTED verdict should cite. Compare [[stack-refused-command-lands-on-backups]]: on a
  stack a refused `flowcontrol` still landed on the backups.

| Fact | Consequence |
| --- | --- |
| **All 48 front ports of the -56 are SFP cages.** Measured 2026-10-08 on tb277: only 1.0.2, 1.0.4, 1.0.8, 1.0.40 and 1.0.48 had copper SFPs (AT-SPTX / AT-SPTXc, 1000BASE-T) fitted | An "empty" port cannot link at all. | `show interface status` reports a fitted copper SFP as `1000BASE-T`, and the x950's **fixed** copper ports as `10GBASE-T` | Media type in that column does not tell you whether a module is fitted. `show system pluggable` does |
| The TPS feature matrix marks ACLs, ACL table utilisation, sequence numbers, `send-to-vlan-port`, **per-VLAN ACLs**, ACLs for SNMPv3 groups, port mirroring and VLAN mirroring (RSPAN) all **supported, priority 1** | None of those may be graded UNSUPPORTED without evidence from the DUT. | `lacp global-passive-mode enable` is in the default config of all three tb277 units | Passive on both ends forms no aggregation, so no auto-enrolment was seen (2026-10-08). With an **active** far end it would enrol a freed port — [[lacp-passive-hides-links-from-stp]] |

## 5. ACL and mirroring CLI — measured and documented

Measured on tb277 (`sin_x96056-20260921-9`) 2026-10-07/08, cross-checked against the guides.

- **Hardware ACL actions** (ACL guide Table 2, p13) — the definitions a verdict is graded
  against: `copy-to-cpu` = copy to CPU **and forward**; `send-to-cpu` = to CPU and **not**
  forwarded; `copy-to-mirror` = copy to mirror port **and forward**; `send-to-mirror` = to the
  mirror port, **not switched**; `deny-and-not-cpu` = drop without reaching the CPU.
  - ⚠ **The guide's table is generic AW+ ("depending on your switch family") and this build
    offers only SIX of them.** Measured 2026-10-08 on `sin_x96056-20260921-9`:
    `access-list 3000 ?` and `access-list 4000 ?` both offer exactly
    `copy-to-cpu  copy-to-mirror  deny  permit  send-to-cpu  send-to-vlan-port`.
    **`send-to-mirror` and `deny-and-not-cpu` are absent** from the numbered forms. Whether they
    exist inside the `access-list hardware <name>` sub-mode is **not yet confirmed** — reaching
    that sub-mode creates the list, which a read-only triage would not do.
  - `copy-to-mirror` additionally takes `interface <port>` ("Mirror interface to send to"), so a
    mirror destination can be named explicitly instead of relying on `mirror interface none`.
  - `send-to-vlan-port` is present, and the TPS marks it supported.
  - ⚠ `send-to-cpu` lands traffic on a CPU queue that *"could result in EPSR healthcheck
    messages and other control packets being dropped"* (guide), and T44989's own precondition
    cites **CR30477** for STP/EPSR interference. Two independent sources. Watch STP state across
    any send-to-cpu case.
- **`access-group` is for ports and aggregators.** Per-VLAN ACLs use a different mechanism
  entirely — `vlan access-map` + `match access-group` + `vlan filter <map> vlan-list <list>
  input` (guide p17). **An absent `access-group` under `interface vlanN` is correct, not a
  defect** — a 2026-10-07 session recorded the opposite inference and it was wrong.
  Measured 2026-10-08: under `interface vlan1`, `access-group`, `service-policy` **and**
  `static-channel-group` all return `% Unrecognized command`, while `vlan access-map WORD` and
  `vlan filter <map> vlan-list` both parse in global config. Both halves now measured.
- **The ingress classifier pool reads 1024 entries**, not the ~3K the TPS's Falcon arithmetic
  implies (measured 2026-10-08, clean DUT: `show platform classifier statistics utilization
  brief` → `Total 2 / 1024`, the 2 being Loop Detection; egress `0 / 6144`). The same pool is
  shared by System, DHCP Snooping, Loop Detection, EPSR, CFM, G8032, Global ACL, ACL, VACL and
  QoS, each separately counted — which makes the Test Strategy's ACL-vs-QoS contention directly
  measurable. **Only `[Instance 0]` is reported, covering `port1.0.1-port1.0.77`**, though the
  TPS describes Falcon as split over two control pipes. Open question against the project's
  2.5K 60-byte rule budget — raised to the Test Engineer 2026-10-08, not yet answered.
- **Apply to a static channel group on the aggregator itself**, not its members; for an LACP
  channel group, apply to every member port (guide, IPv4 hw ACL introduction).
- **Hardware ACLs implicitly PERMIT** what no rule denies; software/standard ACLs implicitly
  DENY. Opposite defaults, easy to grade the wrong way round.
- **Interface ACLs are matched BEFORE QoS policies on the same port** (guide p24). A permit in
  the interface ACL forwards the packet and **bypasses every subsequent QoS rule**. ⇒ when a
  case says "apply the same ACL via service policy and repeat", the `access-group` must be
  removed and proven gone first, or the QoS path is never exercised and the result is a false
  pass. The QoS path is `mls qos enable` → `class-map` `match access-group` → `policy-map`
  `class` → `service-policy input` (guide p24–25); `mls qos enable` prompts (y/n) —
  [[awplus-config-prompts-abort-and-logout]].
- ⚠ Do **not** enable `access-list hardware-deny-log` while any `copy-to-cpu`/`send-to-cpu` ACL
  exists: matching packets are then dropped (guide p14).
- **A standard (1–99) list cannot be bound to an interface** on this platform (measured
  2026-10-07); `access-group` takes 3000–3699, 4000–4699 or a named hardware list. Standard
  lists still bind to `vty access-class` (guide p16).
- **Mirroring** (guide p3–4, 6, 14): **one mirror destination per switch**, local or remote. The
  destination port leaves every VLAN and **stops participating in normal switching**, so it must
  be removed from trunks and VLANs first, and it must not be an STP-discarding port. The command
  is entered on the **destination** port naming the **source** (`mirror interface <src> direction
  transmit|receive|both`), which is why `show mirror interface <X>` keys on the **monitored**
  port. `mirror interface none` makes the port an **ACL-driven** destination for
  `copy-to-mirror`/`send-to-mirror` — it is not an off switch, and `show mirror` then reports
  `none (via ACL)`. `copy-to-mirror` **terminates ACL processing at the first match**, which is
  why `mirror interface <src> vlan <vid>` was added later.
- `% <port> is currently configured as a mirror-port...` is an **advisory, not a rejection** —
  the command succeeds and the prompt advances, but a `% `-matching stop-on-error driver aborts
  on it ([[bench-scripts-stop-on-cli-errors]]).
- `show interface status` reports a mirror destination port identically with and without a
  mirror, so it cannot evidence "returned to normal switching".
- `clock set` is exec-only (no running-config footprint); `clock timezone` is config-mode.
