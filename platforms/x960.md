# x960 — platform facts (AT-x960-56YSQ and AT-x960-28YSQ)

**What this is.** The platform, firmware and CLI behaviour of the x960 family that has cost
hardware hours, been mistaken for a defect, or would otherwise be re-derived. Read it whenever
the DUT's family is x960 (`/orient-dt` §2). Unless a row says otherwise, everything measured
here was measured on **tb277**, on the build it names. What any bench *currently* is (cabling,
boot source today, which ports are cabled) is never written here: that is the box's generated
`bench-state.md`.

## 1. 🔥 The two models do NOT share a switching core

This is the single most load-bearing fact about the family, and it is invisible from the CLI.

| model | switch chip | family | note |
| --- | --- | --- | --- |
| **x960-56YSQ** | **Marvell 98CX8514** | **Falcon** | **no PHYs** — every port connects directly to the switch chip |
| x960-28YSQ | Marvell 98DX4580M | AlleyCat5P-XL | has MACsec support |

Source: TPS. The CPU on both is a Marvell CN9130 (Octeon family) multi-core ARMv8.

**Consequence, and the Test Strategy says it in as many words:** *"The Falcon switching core is
new to this family. Results from the x960-28YSQ demonstrate nothing about this board's
dataplane"* and *"ART on another platform proves nothing about this"*. So:

- A dataplane result from the -28 is **not** evidence about the -56, even though both report the
  same software version and the same `show` output.
- ART/CR history from other platforms (the `1336_acl` suite's CRs were raised on FS980 and
  GS970EMX) points at *where to look*, never at what this board does.
- There is **no reference platform** for Falcon in this project. The Test Strategy's instruction
  is to verify dataplane behaviour from first principles against the TPS limits.

Related: [[corpus-sources-are-not-authoritative]].

## 2. Falcon TCAM — the limit behind most "odd" ACL/QoS behaviour

From the TPS. The TCAM is shared between QoS, ACLs, tunnel terminations and subnet-based VLANs.

| | AC5P-XL (the -28) | **Falcon (the -56)** |
| --- | --- | --- |
| raw | 24K x 20-byte rules | 36K x 10-byte = 18K x 20-byte, **split over two control pipes** |
| usable 20-byte rules | 24K | **9K** |
| ACLs (60-byte rules) | 8K with an AC5P-XL-only silicon profile | **3K max**, if nothing else used the TCAM |

**The project works to a 2.5K 60-byte rule budget**, chosen as the lowest common denominator so
mixed stacking works. The Test Strategy lists *"TCAM consumption against the chosen 2.5K rule
budget on Falcon"* as a named risk, and calls out *"TCAM utilisation and contention with QoS"* as
a coverage area.

- 🔥 **MEASURED 2026-10-09 on tb277 (`sin_x96056-20260921-9`): the DUT reports an ingress
  classifier pool of `Total 2 / 1024`, i.e. 1024 entries — NOT the 2.5K–3K above.** Egress reads
  `0 / 6144`. Only `[Instance 0]` appears, covering `port1.0.1-port1.0.77`, where the TPS
  describes two control pipes. Whether 1024 is correct for this build is OPEN; if it is, the
  project's 2.5K rule budget needs restating. Three further measurements, same session:
  - **one bound rule = exactly one ingress entry** (five lists bound at once read `ACL 5`);
  - **an UNBOUND access-list costs NOTHING** — six defined with one bound reads `ACL 1`, so the
    budget is spent per **binding**, not per definition;
  - **the SAME rule costs 1 entry via `access-group` but 3 via `service-policy input`**
    (`QoS 3`). A QoS-bound ACL is three times as expensive as the identical interface-bound one.
- **Check it with `show platform classifier statistics utilization brief`** (ACL guide p18).
- **🔥 MEASURED 2026-10-08 on `sin_x96056-20260921-9` (T44992), and it contradicts the TPS
  arithmetic.** The ingress pool is **1024 entries**, not the ~3K the TPS implies, and the cost
  per rule depends on how the ACL is applied:

  | state | counters | total |
  | --- | --- | --- |
  | clean DUT | `Loop Detection 2`, all else 0 | `2 / 1024` |
  | one hardware ACL rule via `access-group` on `sa1` | `ACL 1` | `3 / 1024` |
  | the SAME rule via `service-policy input` on `sa1` | `ACL 0`, **`QoS 3`** | `5 / 1024` |

  ⇒ **one rule = 1 entry through `access-group`, but 3 entries through the QoS path.** Ceiling on
  this build is therefore ~1022 rules via access-group and ~340 via service-policy, before any
  other feature takes its share. The pool is shared with Global ACL, VACL, QoS, Loop Detection,
  EPSR, CFM, G8032, DoS, RA Guard, BFD/BEFD, AMFAPPS, IPFIX (Flow + Sample), OpenFlow
  (Hybrid/Flow/Default) and MLAG, each separately counted. Egress is a separate `0 / 6144`.
  The project budget is **2.5K 60-byte rules** and the Test Strategy's headline risk is
  *"TCAM consumption against the chosen 2.5K rule budget on Falcon"*. Raised to the Test
  Engineer 2026-10-08 as a candidate CR in its own right; unanswered.
- **`mls qos enable` prompts and briefly interrupts traffic**: `Traffic will stop while
  configuration is applied. Continue? (y/n):` — answer `y\r`
  ([[awplus-config-prompts-abort-and-logout]]). Because it stops traffic, a control measurement
  taken before QoS was enabled does not carry across it; take a fresh one after.
- When an ACL is accepted but does not take effect, or a QoS policy displaces one, suspect TCAM
  exhaustion before suspecting the feature. The two-pipe split is its own hazard: rules are not
  one flat pool.

## 3. MACsec and flow control are NOT supported on the -56

- **MACsec: not supported on the x960-56YSQ** — the Falcon chip does not have it (TPS). On the
  **-28** it is supported, but **not on ports 17–24** (silicon: MACsec covers only the first two
  DMA groups, lanes 0–15), and on ports 25/29/33/37 it is handled by the 100G uplink PHY and
  works only from 5.5.6-2 onward.
- **Flow Control: `No` — *"Cannot be supported due to a silicon issue"*** (TPS row 155).
  This is what a real platform limit looks like in the TPS, and it is the evidence an
  UNSUPPORTED verdict should cite. Compare [[stack-refused-command-lands-on-backups]]: on a
  stack a refused `flowcontrol` still landed on the backups.

## 5. ACL and mirroring CLI — measured and documented

Measured on tb277 (`sin_x96056-20260921-9`) 2026-10-07/08, cross-checked against the guides.

- **Hardware ACL actions** (ACL guide Table 2, p13) — the definitions a verdict is graded
  against: `copy-to-cpu` = copy to CPU **and forward**; `send-to-cpu` = to CPU and **not**
  forwarded; `copy-to-mirror` = copy to mirror port **and forward**; `send-to-mirror` = to the
  mirror port, **not switched**; `deny-and-not-cpu` = drop without reaching the CPU.
  - ⚠ **A bound NUMBERED hardware ACL cannot be edited; a bound NAMED one can.** Measured
    2026-10-09 (T44987). With `access-group 3000` on a port, `access-list 3000 deny ...` is
    **refused**: `% This access-list is currently attached to an interface so cannot be edited.`
    — the entry is not added. The named sub-mode behaves oppositely: re-entering
    `access-list hardware <name>` prints an **advisory** and the edit succeeds on `exit`/`end`.
    ⇒ to change a numbered list, remove the `access-group` first, edit, then re-apply.
    🔥 **The two `%` strings differ by one word and mean opposite things**
    (`is attached` = advisory, `is currently attached` = rejection). `tools/test_advisory.py`
    pins the pair; never loosen the advisory pattern to span both.
  - ⚠ **The guide's table is generic AW+ ("depending on your switch family") and this build
    offers only SIX of them.** Measured 2026-10-08 on `sin_x96056-20260921-9`:
    `access-list 3000 ?` and `access-list 4000 ?` both offer exactly
    `copy-to-cpu  copy-to-mirror  deny  permit  send-to-cpu  send-to-vlan-port`.
    **`send-to-mirror` and `deny-and-not-cpu` are absent** from the numbered forms. Whether they
    exist inside the `access-list hardware <name>` sub-mode is **not yet confirmed** — reaching
    that sub-mode creates the list, which a read-only triage would not do.
  - `copy-to-mirror` additionally takes `interface <port>` ("Mirror interface to send to"), so a
    mirror destination can be named explicitly instead of relying on `mirror interface none`.
  - `send-to-vlan-port` is present, and the TPS marks it supported.
  - ⚠ `send-to-cpu` lands traffic on a CPU queue that *"could result in EPSR healthcheck
    messages and other control packets being dropped"* (guide), and T44989's own precondition
    cites **CR30477** for STP/EPSR interference. Two independent sources. Watch STP state across
    any send-to-cpu case.
- **`access-group` is for ports and aggregators.** Per-VLAN ACLs use a different mechanism
  entirely — `vlan access-map` + `match access-group` + `vlan filter <map> vlan-list <list>
  input` (guide p17). **An absent `access-group` under `interface vlanN` is correct, not a
  defect** — a 2026-10-07 session recorded the opposite inference and it was wrong.
  Measured 2026-10-08: under `interface vlan1`, `access-group`, `service-policy` **and**
  `static-channel-group` all return `% Unrecognized command`, while `vlan access-map WORD` and
  `vlan filter <map> vlan-list` both parse in global config. Both halves now measured.
- **The ingress classifier pool reads 1024 entries**, not the ~3K the TPS's Falcon arithmetic
  implies (measured 2026-10-08, clean DUT: `show platform classifier statistics utilization
  brief` → `Total 2 / 1024`, the 2 being Loop Detection; egress `0 / 6144`). The same pool is
  shared by System, DHCP Snooping, Loop Detection, EPSR, CFM, G8032, Global ACL, ACL, VACL and
  QoS, each separately counted — which makes the Test Strategy's ACL-vs-QoS contention directly
  measurable. **Only `[Instance 0]` is reported, covering `port1.0.1-port1.0.77`**, though the
  TPS describes Falcon as split over two control pipes. Open question against the project's
  2.5K 60-byte rule budget — raised to the Test Engineer 2026-10-08, not yet answered.
- **Apply to a static channel group on the aggregator itself**, not its members; for an LACP
  channel group, apply to every member port (guide, IPv4 hw ACL introduction).
- **Hardware ACLs implicitly PERMIT** what no rule denies; software/standard ACLs implicitly
  DENY. Opposite defaults, easy to grade the wrong way round.
- **Interface ACLs are matched BEFORE QoS policies on the same port** (guide p24). A permit in
  the interface ACL forwards the packet and **bypasses every subsequent QoS rule**. ⇒ when a
  case says "apply the same ACL via service policy and repeat", the `access-group` must be
  removed and proven gone first, or the QoS path is never exercised and the result is a false
  pass. The QoS path is `mls qos enable` → `class-map` `match access-group` → `policy-map`
  `class` → `service-policy input` (guide p24–25); `mls qos enable` prompts (y/n) —
  [[awplus-config-prompts-abort-and-logout]].
- ⚠ Do **not** enable `access-list hardware-deny-log` while any `copy-to-cpu`/`send-to-cpu` ACL
  exists: matching packets are then dropped (guide p14).
- **🔥 `show access-list counters` DOES NOT INCREMENT on the service-policy path.** Measured
  2026-10-08 (T44992): with the ACL bound by `access-group`, Packet Hits tracked the traffic
  exactly (4 pings → 4 hits). With the SAME ACL bound through `class-map` → `policy-map` →
  `service-policy input`, the deny was **demonstrably enforced** (100% loss) while Packet Hits
  stayed at **0**. ⇒ **never use ACL hit counters as the evidence for a QoS-bound ACL** — a
  working rule reads as a dead one. Use the traffic result, and the `QoS` row of
  `show platform classifier statistics utilization brief`, instead. Whether this is intended or a
  defect is open; it is a candidate CR.
- `no mls qos enable` is rejected (`% Invalid input detected at '^' marker.`); the negation is
  **`no mls qos`**. Note the asymmetry: `mls qos enable` prompts (y/n), `no mls qos` does not.
- **`copy <file> flash:/default.cfg` is refused** — `% Cannot overwrite flash:/default.cfg as it
  is the default config file`. A saved baseline therefore cannot be restored by copying it back
  over the active boot config. Restore by tearing the running-config down and re-saving with
  `copy running-config startup-config`; never `delete flash:/default.cfg` on a netbooting unit,
  which leaves a window with no startup config at all.
- **HOST trap:** Linux drops a secondary address from the testbox NIC when the link bounces —
  `10.38.22.66/27` vanished from `eth4` during the DUT's reload. Re-add any secondary address
  after a reload before using it as a traffic control (measured 2026-10-08).
- **A standard (1–99) list cannot be bound to an interface** on this platform (measured
  2026-10-07); `access-group` takes 3000–3699, 4000–4699 or a named hardware list. Standard
  lists still bind to `vty access-class` (guide p16).
- **Mirroring** (guide p3–4, 6, 14): **one mirror destination per switch**, local or remote. The
  destination port leaves every VLAN and **stops participating in normal switching**, so it must
  be removed from trunks and VLANs first, and it must not be an STP-discarding port. The command
  is entered on the **destination** port naming the **source** (`mirror interface <src> direction
  transmit|receive|both`), which is why `show mirror interface <X>` keys on the **monitored**
  port. `mirror interface none` makes the port an **ACL-driven** destination for
  `copy-to-mirror`/`send-to-mirror` — it is not an off switch, and `show mirror` then reports
  `none (via ACL)`. `copy-to-mirror` **terminates ACL processing at the first match**, which is
  why `mirror interface <src> vlan <vid>` was added later.
- **Two `%` lines on this platform are ADVISORIES, not rejections.** The command succeeds and the
  prompt advances, but a `% `-matching stop-on-error driver aborts on either
  ([[bench-scripts-stop-on-cli-errors]]). Measured 2026-10-07/08:
  - `% <port> is currently configured as a mirror-port...`
  - `% This access-list is attached to an interface. The modified configuration will be applied
    to the interface automatically after exiting this configuration mode by entering "exit" or
    "end" command.` — re-entering `access-list hardware <name>` while it is bound to an
    interface. Note what it also tells you: **edits to a bound hardware ACL do not take effect
    until you leave the sub-mode**, so a counter read before `exit`/`end` reflects the OLD rule.
- **The named hardware ACL sub-mode offers `mac` where the numbered IP form does not.** Measured
  2026-10-08 in `(config-ip-hw-acl)`: `deny ?` → `icmp ip mac proto tcp udp`, against the
  numbered `access-list 3000 deny ?` → `icmp ip proto tcp udp`. (Closes triage issue I-8.)
- **Hardware ACLs are INGRESS.** `access-group` on a port or aggregator filters what arrives on
  it. An ACL on `saN` therefore never sees a flow that merely egresses `saN` — write the rule for
  the direction that ingresses the bound interface, and source the traffic accordingly, or it
  cannot match and the zero counter reads like non-enforcement.
- 🔥 **Mirror status output does NOT describe the dataplane. Measured 2026-10-09 on tb277,
  `sin_x96056-20260921-9`, all three proven by frame capture at the destination:**
  1. **`direction both` copies NO frames at all**, while `show mirror`, `show mirror interface
     <src>` and the running-config all report it correctly, and it survives a save and reload.
     Proven on a pristine boot (saved to flash, DUT reloaded, so no re-application history could
     be blamed), where `transmit` and `receive` applied on that same boot each delivered their
     frames. Reproduced 5x. **FAIL-grade defect**, case T44969.
  2. **A RE-APPLIED mirror copies nothing until the destination port is bounced**
     (`shutdown` / `no shutdown`). Only the first-ever mirror on a port works immediately.
  3. **An in-place `direction` change is SILENTLY IGNORED** — no error, and `show mirror` keeps
     reporting the OLD direction, which the dataplane also keeps using. `no mirror interface
     <src>` must come first.

  ⇒ **Never grade a mirroring case from `show mirror`.** Remove → apply → bounce the destination
  → then capture frames. Five mirroring cases would have passed on a status read-back alone.
- `show interface status` reports a mirror destination port identically with and without a
  mirror, so it cannot evidence "returned to normal switching". **A capture can:** measured
  2026-10-08 (T44973), the moment the mirror is removed the destination port starts carrying
  normal traffic again and the host NIC sees LLDP and VLAN-1 broadcast. That is the only
  available proof for that step.
- `clock set` is exec-only (no running-config footprint); `clock timezone` is config-mode.

### 🔥 Port mirroring: three defects, and why `show mirror` cannot be trusted

Measured 2026-10-08/09 on `sin_x96056-20260921-9` (campaign `mirror-2026-10-08T1637`, cases
T44967–T44974). All three are reproducible, none is in any case's step text, and **none of them
is visible from the CLI** — in every one, `show mirror` reports the mirror `Enabled` with the
right direction and source while the dataplane does something else.

| | defect | what the CLI shows |
| --- | --- | --- |
| **M1** | A **re-applied** mirror copies nothing until the destination port is bounced (`shutdown` / `no shutdown`). Only the first mirror ever applied to a port works immediately. | `Enabled`, correct direction |
| **M2** | An **in-place `direction` change** over an existing mirror is accepted with no error and is silently discarded. The dataplane keeps the old direction too. `no mirror interface <src>` must come first. | the **stale** direction |
| **M3** | **`direction both` copies NO frames at all**, and survives a save and reload in that state. | `Enabled`, `direction both` |

The discriminator for M3, one boot, one cabling, one 6-ping flow, same procedure — and the
capture sizes are the evidence, 1 byte meaning nothing arrived:

| direction | capture | echo requests | echo replies |
| --- | --- | --- | --- |
| `transmit` | 535 B | 0 | 6 ✅ |
| `receive` | 547 B | 6 | 0 ✅ |
| **`both`** | **1 B** | **0** | **0** ❌ |

M1 was ruled out as the cause of M3 by using a reload: `both` was saved to startup and the DUT
rebooted, so on that boot there was no re-application history at all, and it still copied
nothing — while `transmit` and `receive` applied on that same boot both worked. Also ruled out
before grading: settle time, a second destination bounce, link state at both ends, host capture
(`tcpdump` reported `0 packets received by filter` on an unfiltered run) and a wedged mirror
engine (re-applying `transmit` mid-session worked at once).

**⇒ Never accept `show mirror` as proof that mirroring works on this platform.** Every mirror
verdict needs frame-level capture at the destination. A test that reads back `show mirror` and
stops there records a pass on all three of these. The working method that does hold:
`no mirror interface <src>` → apply → **bounce the destination** → only then measure.

Evidence: `tb277/x960/mirror-2026-10-08T1637/` — T44969's log for M3, T44968's for M1 and M2,
plus `work-box/` for the raw captures. CR wording was left to the Test Engineer; these are
measurements, not graded product judgements.

## 6. DHCP server, DHCP relay and DNS relay — measured 2026-10-15

Measured on tb277, **AT-x960-56YSQ S/N A2WQS700B, `sin_x96056-20261012-24`**, six AWPTCM cases
(`tb277/x960/dhcp-*-2026-10-15T1458/`), all PASS. Each item below would otherwise produce a
confidently wrong verdict next time.

### 6.1 🔥 A relayed DHCP frame is INVISIBLE to scapy unless BOOTP is bound on dport alone

An AW+ relay forwards the client frame from an **ephemeral source port**, not from 67. scapy's
default binding is on the source port, so a sniffer that does not rebind decodes **nothing** —
and the run reads as *the relay is dropping every packet*. Before reading any relayed capture:

```python
bind_layers(UDP, BOOTP, dport=67); bind_layers(UDP, BOOTP, dport=68)
```

Measured: a scapy server received 0 frames, then 5, after those two lines and no other change.
`tools/dhcp4.py` and `tools/opt82dump.py` both carry the fix.

### 6.2 `ip dhcp-relay agent-option checking` validates SERVER RESPONSES, not client ingress

The name reads like an untrusted-ingress check. It is not: it polices what comes **back** from
the server. Measuring it on the ingress side proves nothing, and a case designed around
"the relay should drop a client frame that already carries option 82" tests the wrong direction.
The ingress behaviour is `ip dhcp-relay information policy` instead (replace / keep / drop /
append), and all four were measured correct.

### 6.3 `probe type ping` ARPs FIRST — "no ARP" does not discriminate the two probe types

For a locally connected client the ping probe sends ARP before it sends ICMP, then escalates.
So the presence or absence of ARP frames cannot tell `probe type arp` from `probe type ping`.
Discriminate on the ICMP echo instead. Related: under `probe type ping`, an ARP reply **alone**
does not withhold the address — only the ICMP echo reply does — which is narrower than the
literal "or" in the ARP Probe TFS S1566.1.01.

### 6.4 ⚠️ Two near-identical `% …already…` messages mean OPPOSITE things

| message | meaning | state |
| --- | --- | --- |
| `% DHCP Relay is already globally enabled` | **advisory** | the state holds; carry on |
| `% DHCP client is already running on this interface.` | **genuine rejection**, exit 2 | the config was NOT applied |

Measuring past the second one captures the **default** DHCP client and reports it as the
configured one. A gate that treats every `%` line as fatal is also wrong here: `% Can not
configure DHCP Relay agent option remote-id unless agent option is set` is the *expected* result
of a negative step.

### 6.5 All SVIs share ONE MAC, so option 61 cannot identify which interface was named

`vlan1`, `vlan10` and `vlan48` all read `e01a.ead4.7043`, so `ip address dhcp client-id vlan10`
and `... client-id vlan48` emit **byte-identical** option 61. Grade such a case on presence, type
byte and length, and say so; a content comparison proves nothing. Check
`show running-config interface vlanN` for the keyword before capturing.

### 6.6 The DHCP client's parameter request list is [1,3,15,6,43]

Option **43** is additional to what the wiki DHCP page documents (1/3/6/15). Not a defect;
expect it, and expect `request vendor-identifying-specific` to append **125** to that list.
`vendor-identifying-class` emits option 124 carrying IANA enterprise **207** (Allied Telesis).

### 6.7 A DHCP-learned DNS server is queried in PREFERENCE to a statically configured one

Measured with two responders on one NIC answering different A records: the relay queried the
DHCP-learned `.2` and **never ARPed** for the static `.9`; a control with `.9` alone proves `.9`
is reachable and used. DNS Relay TFS S1570.1.12 says DHCP-learned servers are "added **last**",
which describes list position — a resolver need not walk its list in order, so this is an
observation, not a defect. **`show ip name-server` cannot settle it either**: its display is
type-grouped, and it lists the dynamic entry first regardless of configuration order.

### 6.8 🔴 Any DNS or DHCP-client change restarts the relay process — wait 20 s before counting

Documented in the DNS Relay TFS "Limitations"; measured here. A leg run ~3 s after such a change
forwarded **nothing** and read as *the DUT cannot use a statically configured DNS server*. The
identical configuration after a 20 s settle forwarded every query and ARPed for the server first.

### 6.9 Open: is the DNS forwarding cache meant to cover RELAYED queries?

With `ip dns forwarding cache size 100 time 60` and `DNS Cache: enabled, Size 100, Max-TTL 60`,
two identical queries 5.3 s apart **both** went upstream. Not graded a failure: the TFS separates
a *Name Resolver Process* from a *DNS Relay Process*, and S1570.1.03/.11 both say "name **resolve
result**", which plausibly scopes the cache to the device's own lookups. Nothing on the bench
separates "not cached by design" from "cache broken". **This wants a developer's answer, not
another bench run.** Evidence: `tb277/x960/dhcp-client-2026-10-15T1458/T43854/T43854.log`.

## 7. IPv4 unicast routing — measured 2026-10-15 (static, ECMP, secondary addresses)

From `tb277/x960/static-2026-10-15T1747/` (T43855, T43861, T43862), AT-x960-56YSQ
`sin_x96056-20261012-24`. Every item below was measured in the **dataplane** with crafted frames
and per-egress-port counters, never read off `show ip route`. Read this before the next x960
routing work; §7.3 and §7.6 will otherwise cost you a wrong verdict.

### 7.1 🔥 ECMP is PER-FLOW, not per-packet — the Route Selection guide says the opposite

The Route Selection Feature Overview and Configuration Guide (C613-22029-00 REV G, p.10) states:
*"On AlliedWare Plus switches, ECMP calculations are done on a per-packet basis. This means that
the packets in a flow may take different paths."* **Measured: 400 packets of a single flow all
took the same egress port**, with the other path proven forwarding in the same minute. Treat the
guide's sentence as wrong for this platform. (Per-flow is the better behaviour — per-packet
reorders TCP — so this reads as a documentation defect, not a product one.)

### 7.2 🔥 The ECMP hash uses the IPv4 SOURCE and DESTINATION ADDRESSES ONLY

| what varied across 64 flows | split across the two egress ports |
| --- | --- |
| destination address | ~50 / 50 |
| source address | ~50 / 50 |
| **source port** | **1280 / 0 — no spread at all** |
| **destination port** | **1280 / 0 — no spread at all** |

L4 ports are not hash inputs. A deployment whose flows differ only in port (one client, one
server, many sessions) gets **no** load sharing. Undocumented anywhere in the guide.

**The matching instrument trap:** vary the two addresses in LOCKSTEP and the entropy largely
cancels — an evenly-hashing device then reads as 81/19. Decorrelate the spans
(`tools/ecmpflows.py --src-span 64 --dst-span 7`) or vary one field per leg.

### 7.3 🔥 An ECMP next hop with unresolved ARP is silently absent from the dataplane

`show ip route database` marks it `*>` (selected AND FIB route) exactly as it does a live path.
Seen straight after a reboot: both static routes present, both ports Forwarding, both `*>` — and
**100% of traffic took the one next hop whose ARP was resolved**. Pinging the other next hop
restored the 50/50 split immediately. **Check `show arp` for every next hop before believing an
ECMP route group**, and never grade ECMP on the route table.

### 7.4 Administrative distance behaves as documented, including the 255 rule

- A floating static (distance 250) stays out of the FIB while a distance-1 route exists, and
  takes over on its removal — verified by the **egress port moving**, attributed on the wire by
  ICMP unreachables sourced from the new next hop rather than from the DUT.
- **Distance 255 reaches the RIB and NOT the FIB**: `show ip route database` lists it with no
  `*>`, `show ip route` omits it entirely, and nothing is forwarded. As the guide states.
- `maximum-paths` is `<1-8>`; the default is absent from running-config (guide says the default
  group size is 4 — **not verified**, the bench has only two usable routed legs).

### 7.5 ⚠️ `show ip route <address>` prints the NON-selected route when a prefix has two

With a distance-1 and a distance-250 route for one prefix, `show ip route <address>` printed the
**250** entry and dropped the `best` / `*` markers, while `show ip route` and `show ip route
database` both correctly showed the distance-1 route as the FIB route. Forwarding was correct
throughout. A floating static graded on `show ip route <address>` alone reads exactly backwards.
**`show ip route database` is the trustworthy read-back** (legend: `> selected, * FIB`).

### 7.6 🔥 ARP is answered only when the SENDER is inside the target address's own subnet

On an SVI with a primary and a secondary address, measured symmetrically:

| ARP sender | who-has primary | who-has secondary |
| --- | --- | --- |
| in the primary subnet | **answered** | silent |
| in the secondary subnet | silent | **answered** |

So the guide's *"treats secondary addresses the same as primary addresses ... such as responding
for ARP requests"* **holds** — both obey the same rule. But a tester who ARPs for a secondary
address from a host in the primary subnet measures silence and will wrongly record a defect.
All SVIs share one MAC (§6.5), so only the target address distinguishes them.

### 7.7 Secondary addresses: the ordering rules are enforced, with clear messages

- `ip address <a>/<m> secondary` on an interface with no primary → `% Configure primary first <if>`
- `no ip address <primary>` while any secondary exists → `% Must delete secondary before deleting
  primary`, and **the configuration is left untouched** — refused, never cascaded.
- Multiple secondaries coexist, each getting its own connected route. The 32-address limit was
  **not exercised**.
- `show ip interface brief` shows **only the primary** — it cannot tell you whether a secondary
  exists. `show interface <if>`, `show running-config` and `show ip route` all do.
- The DUT ARPs for a host in the secondary subnet as `tell <secondary>`, i.e. it uses the
  secondary as its own identity there.

### 7.8 Things that do NOT discriminate, so do not build a leg on them

- **A frame merely SOURCED in a subnet.** Forwarding is destination-based and there is no uRPF,
  so a frame from an unconfigured source subnet crosses the DUT just the same. Caught at the
  baseline-off leg of T43862 before it could produce a false PASS.
- **A `ping` across the DUT.** It cannot say which path, which route, or whether the route under
  test was used (STANDING-ORDERS §7).
- **ICMP destination-unreachable COUNTS.** Generation is rate-limited — about 2 per 10 unroutable
  packets for network-unreachable. Their **source address** is excellent attribution; their
  count is not a measurement. (Host-unreachable, from an on-link route that cannot ARP, was not
  rate-limited in the same way: 5 per 5.)

### 7.9 Expected values, so the next run compares instead of discovering

| thing | value on this build |
| --- | --- |
| reload to `login:` | **60–68 s** (three reloads: 68 s, 60 s, 61 s) |
| idle counter drift per port | ~**1.6 packets/s** (STP + LLDP), symmetric across ports |
| `ip route` interface form | installs as `is directly connected, <if>`; on a VLAN it then ARPs for the destination and answers **t3/c1 host**-unreachable, not t3/c0 network-unreachable |
| static route display | every static route prints `weight 1` even though weighted lottery is a firewall/VPN-router feature — **effect on a switch not measured** |
| STP | single-instance `rstp`; see §7.10 |

### 7.10 🔴 Single-instance RSTP: two parallel links between one pair of bridges can never both forward

`spanning-tree mode rstp` is single-instance, so it computes one tree over the **physical**
topology and a Discarding port is blocked for **every** VLAN. Giving each routed leg its own
VLAN frees nothing. Consequences for bench design:

- **Two parallel links to the same partner cannot both carry an ECMP path**, whichever bridge is
  root. Use **one link to each of two partners** instead — a loop-free star, with spanning tree
  left enabled.
- To free a DUT's routed legs, make the **DUT the root bridge** (`spanning-tree priority 0`,
  `<0-61440>` in steps of 4096): every port on the root is Designated and Forwarding, and the
  blocking moves onto the partners' spare ports.
- Shut the DUT end of any redundant link whose partner end you must not touch, so the partner's
  root-port choice is forced rather than decided by a bridge-ID or port-ID tie-break.
- A `spanning-tree mode` change silently drops `no spanning-tree <mode> enable`
  ([[stp-mode-change-reenables-spanning-tree]]).

## 7A. IGPs — OSPFv2 and RIP v1/v2, measured 2026-10-15 (group C)

From `tb277/x960/igp-2026-10-15T1747/` (T43857, T43856), AT-x960-56YSQ `sin_x96056-20261012-24`,
with an x960-28YSQ and an x950 GEN2 as the two IGP peers. Every forwarding claim below was
measured in the **dataplane** with crafted frames, and every protocol-behaviour claim was read
out of the **protocol's own packets** on a host NIC, never off a `show`.

### 7A.1 🔥 `service <proto>` and `router <proto>` cannot share a console batch

| time after `service ospf` | `router ospf 1` |
| --- | --- |
| ~1 s | **rejected**: `% OSPF protocol daemon is not running or feature license is not available` |
| within 7 s | accepted |

Measured on all three units. The OSPF Feature Overview Guide prints the two as consecutive
lines to type, which a human does slowly enough and a script does not. Two further traps ride
on it: the rejection makes `tools/cfg.py` abandon the rest of its batch, and the message blames
the **licence** as well as the daemon — on a unit that holds `OSPF-FULL`/`RIP-256` that half is
a red herring and must never be read as UNSUPPORTED. Send the `service` line in its own batch
and wait ~10 s (T43856 did, and saw no rejection on any unit).

### 7A.2 🔥 `no service <proto>` writes a STICKY config line on a unit that BOOTED with the service

A unit whose boot config contained `service ospf` keeps **`no service ospf`** in
running-config after `no service ospf`, for ever. A unit that only ever had the service applied
at runtime keeps nothing. Measured side by side on three units in the same minute, and the
distinguishing factor is the boot, not the daemon: after a second reboot `show process | include
ospf` returns **nothing at all** and the line is still there.

⇒ **Every reboot-persistence limb on a service-gated protocol leaves such a line, and that
case's teardown diff cannot come back clean.** It is cosmetic (semantically the default: no
process, no daemon, `show ip ospf` reads "OSPF Routing Process not enabled"), but it is a real
running-config difference and configuration alone will not remove it. The only remedy is to
reload from a config that never mentioned the service.

### 7A.3 ⚠️ F-3 is narrower than §7.3 implies: it is an ECMP-group effect

Straight after a reboot with RIP configured, the DUT's ARP table was **completely empty** while
three RIP routes sat in the FIB pointing at unresolved next hops — a harder version of §7.3,
because RIPv2 talks to 224.0.0.9 and so **nothing primes the next hop** (an OSPF adjacency, by
contrast, resolves it for free). The leg was run cold on purpose: **15 of 15 frames forwarded,
none lost, and the ARP table filled itself from the traffic.** So a **single-path** route with
an unresolved next hop resolves on demand and forwards everything. §7.3's hazard belongs to
**ECMP group membership**. Check `show arp` before believing an ECMP route group; you need not
before a single-path leg.

### 7A.4 OSPFv2 — measured values and behaviours

| thing | value on this build |
| --- | --- |
| adjacency to Full | **17 s** from `router ospf 1` (two neighbours, two interfaces, simultaneously) |
| after a reboot | still `ExStart` 43 s after login; **Full and both routes installed by ~78 s** after the reload was issued. A persistence limb that reads the table too early reports the feature lost |

### 7A.5 RIP — measured values, and the v1/v2 difference on the wire

Default is **version 2 on every interface** (`Default version control: send version 2, receive
version 2`), confirming the RIP guide. Timers as reported and as measured: updates every 30 s
±5 s, **timeout 180 s**, **garbage collect 120 s**, AD **120**.

| | version 2 | version 1 |
| --- | --- | --- |
| IP destination | 224.0.0.9 | **subnet broadcast** (192.168.10.255) |
| Ethernet destination | 01:00:5e:00:00:09 | **ff:ff:ff:ff:ff:ff** |
| TTL | 1 | **64** |
| prefix length / mask | on every entry | **absent** |
| route tag, next-hop, AFI | present | absent |
| 10.0.41.0/30 + 10.0.61.0/30 + two 10.x /32s, sent out a 192.168.10.0/24 interface | four entries | **one classful `10.0.0.0`** |

- **A /32 host route DOES survive v1** when advertised on an interface in the **same major
  network** — the receiver reads a non-zero host part as a host route. The classful collapse
  above happens only across a major-network boundary. Both are the same rule; they look
  contradictory in a log if you do not say which interface each was measured on.
- **A global `version 1` loses a v2-only neighbour after exactly the 180 s timeout**, and that
  neighbour disappears from `Routing Information Sources` with **Bad Packets 0 / Bad Routes 0** —
  the v2 updates are not errors, they are simply not accepted. Returning to v2 re-learns in ~6 s.
- 🔥 **Withdrawal POISONS, it does not merely time out.** `no network <prefix>` on the neighbour
  produced a **triggered update at metric 16**: the route left the FIB in **13 s**, then sat in
  `show ip rip database` at metric 16 while the 120 s garbage-collect timer counted down, then
  vanished. **`show ip route` cannot tell that apart from a 180 s timeout** — the database can.
- **Split horizon with poisoned reverse is on by default**: the capture shows the DUT
  re-advertising an interface's own network back out of it at metric 16.
- A prefix needs a **natural-class mask** to be testable under v1. `192.168.70.0/24` (class C)
  crosses unchanged; anything inside `10/8` does not, and a `10.x` control flow can be captured
  by a classful `10.0.0.0` advertisement. Pick controls outside `10/8`.

### 7A.6 Method note — what actually carried these two cases

Seventeen counted legs, all `tools/arpleg.py --icmp`, each sending **subject(s) + an unrouted
control + the DUT's own address as an instrument control** in one 20–25 frame capture, with the
reply's SOURCE address giving far-side attribution. Two things made the negative legs
trustworthy, and both are cheap:
- **a second neighbour advertising a second prefix**, so every withdrawal leg has a live
  positive control in the same capture — and better still, **two prefixes from the same
  neighbour over the same port**, which rules out link, port, neighbour, adjacency and
  instrument at once;
- **one `tcpdump -c 1 -v` per protocol state**, after adding the host's VLAN to the protocol's
  `network` statements. It is the only thing that can prove *which protocol version* ran; no
  `show` command can. ~2 KB and a few seconds each.

## 7B. BGPv4 and VRF-Lite — measured 2026-10-15 (group D)

From `tb277/x960/bgp-vrf-2026-10-15T1747/` (T43858, T43859), AT-x960-56YSQ
`sin_x96056-20261012-24`. Twenty-three counted dataplane legs between the two cases, every one
with an unrouted control at zero and the DUT's own address answering, plus four BGP protocol
captures taken **on the DUT itself**. Read §7B.1 and §7B.6 before the next x960 routing run;
either one will otherwise cost a wrong verdict.

### 7B.1 🔥 BGPv4 is NOT service-gated — the opposite of OSPFv2 and RIP on the same software

§7A.1 says `service <proto>` and `router <proto>` cannot share a console batch. **That does not
apply to BGP, and following it breaks the run.**

| | OSPFv2 / RIP (§7A.1) | **BGPv4** |
| --- | --- | --- |
| daemon at boot | not running | **`bgpd` running, pid assigned at boot** |
| `show ip <proto>` before configuring | `% … daemon is not running or feature license…` | **empty output, no `%`** |
| `router <proto>` with no `service` line | **refused** for ~7 s | **accepted immediately** |
| `service <proto>` | enables the daemon | **only completion is `evpn`**; bare form is `% Incomplete command.` |
| `no service <proto>` after a reboot | sticky config line (§7A.2 / F-5) | **nothing — there is no line to negate** |

Measured on an `atlnz`-licensed x960-56 and a Base-licensed x960-28 in the same minute.
Two consequences:
- A script that sends `service bgp` first gets a `% ` line, and `tools/cfg.py` then **abandons
  the rest of the batch** — the whole BGP configuration silently does not happen, and BGP looks
  broken. This is the §7A.1 trap with the sign reversed.
- A BGP reboot-persistence limb leaves **no** F-5 residue, so its teardown diff **can** come
  back clean. T43858's did, on all three devices.

### 7B.2 Capturing a unicast control-plane protocol: the DUT's own `tcpdump`

BGP is unicast TCP between two router addresses, so it never reaches a host NIC on another
segment. Two instruments work, and group D used both.

**The one to reach for: AW+ has `tcpdump` at privileged exec** (`tcpdump ?` → `LINE`, `vrf`,
`<cr>`). Run it on the DUT's console and trigger the event from the **partner's** console, so
only one driver ever touches one `/dev/uN`:
```
awplus# tcpdump -i vlan61 -c 1 -nn -v tcp port 179 and greater 90
```
- **`greater N` counts the 14-byte Ethernet header.** A 19-byte BGP Keepalive is an **85-byte
  frame**, so `greater 75` still matches keepalives. **`greater 90`** isolates UPDATEs
  (announce 114 B, withdraw 94 B) from keepalives and bare ACKs — one packet instead of twenty.
- Give `-c` a count the traffic will certainly reach; keepalives every 30 s fill it eventually,
  so the console cannot be left parked in a blocked `tcpdump`.
- It decodes BGP fully: OPEN with version/AS/holdtime/capabilities, UPDATE with ORIGIN, AS_PATH,
  NEXT_HOP and the NLRI, withdrawals, and NOTIFICATION with its cease subcode.

**A port mirror also works here, contrary to what this tester first recorded.** `mirror
interface port1.0.16 direction receive` on `port1.0.48`, with the destination bounced after
applying (the §5 method), **did copy frames**: the capture holds the mirrored ICMP echo replies
ingressing the monitored port and then the whole mirrored BGP session teardown and
re-establishment on TCP/179. §5's three defects (M1 re-application, M2 in-place direction
change, M3 `direction both`) are unchallenged and still apply — `direction receive`, freshly
applied and bounced, is simply not one of them.

🔴 **The real trap, and it nearly produced a false product finding: a `tcpdump -w` FILE SIZE
read right after an unverified kill is not a measurement.** The file read 0 bytes immediately
after the leg, and that was taken as "the mirror copied nothing". In fact the `kill -INT` had
not reached the tcpdump process at all, so nothing had been flushed to disk; the same file,
once the process was really stopped, held the mirrored frames with timestamps inside the leg's
own window. §5's own evidence is built on capture sizes, so this caution belongs beside it:
**confirm the capture process has exited (`ps`), or read tcpdump's own
`N packets captured` line, before concluding that nothing arrived.**

Two mirror side-effects that ARE real and were measured here:
- `interface <mirror-destination-port>` emits `% … is currently configured as a mirror-port.
  Use caution when altering its config`, which `cfg.py` treats as an error — combined with the
  asynchronous `entered disabled state` lines of the following `shutdown`, a batch stopped and
  **left the port shut**.
- Configuring a port as a mirror destination **removes it from its access VLAN**, and
  `no mirror interface` does not put it back. Re-apply `switchport access vlan N` explicitly.

### 7B.4 🔥 `show running-config` and `copy running-config` disagree about `bgp graceful-restart`

Creating `router bgp <asn>` makes `show running-config` render ` bgp graceful-restart` — nobody
configures it. At the same moment, `copy running-config flash:/<file>` writes
**` no bgp graceful-restart`**, and the DUT's own OPEN advertises **no** Graceful Restart
capability; after booting from that file `show running-config` reads `no bgp graceful-restart`
and `show ip bgp neighbors` lists only route refresh, 4-octet ASN and IPv4 unicast.
⇒ **the display is the thing that is wrong**; the saved file and the wire agree. Same class as
`show mirror` (§5) and `show ip route database` (§7.3). It also means a `.cfg` captured from
`show running-config` is not byte-identical to what `copy running-config` writes.

### 7B.5 ⚠️ `show ip bgp` marks a path `best` even when the FIB is using another protocol

With a static at AD 1 over an eBGP route, `show ip bgp <prefix>` still prints
`valid, external, best` while `show ip route <prefix>` correctly reads
`Known via "static", distance 1`. Those are two different "best": BGP picks the best BGP path,
then the RIB compares that path's AD against every other protocol's. Grade forwarding on the
wire, never on `show ip bgp`.
Also: **`show ip route database <address>` is `% Invalid input`** on this build — `show ip route
database` takes no address argument, unlike `show ip route <address>` (§7.5).

### 7B.6 🔴 VRF-Lite: removing a static inter-VRF route does NOT stop the traffic

After `no ip route vrf red 192.168.48.0/24 vlan48`, with the line gone from running-config and
`show ip route vrf red 192.168.48.2` answering `% Network not in table`, **5 of 5 crafted frames
still crossed from VRF red into VRF blue's segment**, reproduced over three legs and ~2 minutes.
Mechanism, measured: a second host on the same /24 that had never been forwarded to was
correctly blocked (0/5), so the route really is gone and what survives is a **stale ARP-derived
per-host forwarding entry** programmed while the route existed. Remedy, measured:
**`clear arp-cache vrf <name>` stops it immediately.**
Security-relevant, because VRF-Lite is documented as providing "securely isolated" routing
domains: config and route table both say the path is closed while traffic keeps flowing.
**Isolation from a cold start is complete and immediate** — this is a property of inter-VRF
route REMOVAL, not of VRF-Lite.

### 7B.7 VRF-Lite — the rest, all confirmed against the guide (C613-22142-00 REV B)

| behaviour | measured |

| reboot | VRFs, their loopbacks, their separated tables, the isolation and the inter-VRF routing all survive; `show arp` is completely empty afterwards and the first frames resolve on demand (§7A.3) |

### 7B.8 Two post-reboot habits this group confirms

- **Re-read STP before measuring.** `port1.0.48` read `Designated Discarding` 17–21 s after
  `login:` on both reloads and `Designated Forwarding` ~15 s later. A leg measured in that
  window reads as a feature failure.
- **A "zero" leg's stray frame must be identified, not dismissed.** One post-reboot isolation
  leg had exactly one frame on the far NIC: `ARP-REQ who-has 192.168.48.1 tell 192.168.48.1`,
  the DUT's own gratuitous ARP as the SVI came up. Zero of the subject frames crossed.

## 7C. BFD and VRRP — measured 2026-10-16 (group D)

From `tb277/x960/bfd-vrrp-2026-10-16T1406/` (T47201, T47873), AT-x960-56YSQ
`sin_x96056-20261012-24` with an x960-28YSQ (Base licence) as the partner on a `vlan 10` /
`vlan 61` trunk. Thirteen counted dataplane legs, every one with an unowned-MAC or unrouted
control at zero and an instrument control answering, plus seven protocol captures taken with
the DUT's own `tcpdump` (§7B.2).

### 7C.1 🔥 BFD exists and works, but NOTHING binds it to RIP

| | result |
| --- | --- |
| licence | **no BFD bit exists**; BFD is service-gated only. Its refusal says `% BFD protocol daemon is not running` with **no licence clause**, unlike RIP/OSPF/PIM/VRRP which add "or feature license is not available". That missing clause is how you tell the two gate kinds apart without `show license` |
| `service bfd` | starts `bfdd` and `frr-bfdd`; `show bfd peer` then prints `BFD Peers:` with no `% ` |
| configuring a session | `bfd peer <A.B.C.D\|X:X::X:X> [interface IFNAME\|local-address\|multihop\|vrf]` in **global** config — **no routing protocol is needed at all**. Also `bfd echo` and `bfd profile WORD` |
| default timers | detect-multiplier **3**, RX **300 ms**, TX **300 ms**, echo RX 50 ms, echo TX disabled ⇒ detection time **900 ms** |
| on the wire | bidirectional UDP/**3784**, TTL **255**, TOS 0xc0, 52-byte frames, ~240 ms apart (300 ms with RFC 5880 jitter) |
| measured detection | **~1.4 s** (RIP v2 run) and **~1.1 s** (v1 run) from a far-end SVI `shutdown`, with `Diagnostics: control detection time expired` |
| `show bfd session` | **DOES NOT EXIST** — `% Invalid input detected`. The verb is `show bfd peer` (`brief`, `<addr> counters`, `vrf`) |
| the RIP binding | **absent**. The complete 24-command `config-router` list for RIP has no `bfd`; `ip rip ?` offers `authentication receive receive-packet send send-packet split-horizon` and nothing else; `bfd ?` is `% Unrecognized command` in interface AND router-rip mode; `neighbor <addr> ?` offers only `<cr>`. On the SAME interface, `ip ospf ?` **does** offer `bfd`. The RIP Feature Overview Guide has 0 occurrences of "bfd" |

🔴 **The consequence, measured.** On a silent neighbour failure — the far end's SVI shut while
the link and the local SVI stay up, which is the failure BFD exists for — BFD knew in ~1.4 s and
RIP removed the route **~171.6 s** later (its 180 s timeout from the last update received). In
between, a counted leg read **0/5** with its instrument control at 5/5 while
`show ip route <prefix>` read `Known via "rip", distance 120, metric 2, best`. Three instruments,
one instant, disagreeing. ⇒ a case titled "BFD with RIP" is **UNSUPPORTED** on this platform,
and that verdict is only honest if the log carries a working BFD session beside the refusals.

⚠️ **`no service bfd` silently exits configuration mode.** The command is accepted and the
prompt goes `awplus(config)#` → `awplus#`, so the next command fails with `% Invalid input` and a
stop-on-error driver abandons the batch. Put it LAST. (Same family as `mls qos enable`.)

⚠️ **A BFD state change writes NOTHING to the device log** — four transitions, nothing in
`show log | include bfd`. The only record is `show bfd peer`'s `Uptime:`/`Downtime:` field, at
1 s resolution, lost when the session re-establishes.

⚠️ **This build's `tcpdump` mislabels BFD control packets** `BCM-LI-SHIM ... (invalid)`. Identify
them by port 3784, TTL 255 and the 52-byte length, not by the decoder line.

### 7C.2 VRRP — it is VRRPv3 for IPv4, and you cannot read that off the configuration

`service vrrp` is the gate (`show vrrp` → `% VRRPD protocol daemon is not running or feature
license is not available`). VRRP **is** a Base-licence bit on all three tb277 units.

| thing | value on this build |
| --- | --- |
| **`version` command** | **DOES NOT EXIST** — `% Unrecognized command`. The guide upgrades v2→v3 by changing the software release and rebooting, not by a command |
| what the wire says | `VRRPv3, Advertisement, vrid N, prio P, intvl 100cs`, IP proto 112 to 224.0.0.18, TTL 255, Ethernet source = the virtual MAC |
| virtual MAC | `0000.5e00.01<vrid>` as RFC says — vrid 10 ⇒ `00:00:5e:00:01:0a` — in the ARP reply's payload **and** the reply's Ethernet source. This is the only address on a DUT segment that is not the shared SVI MAC (§6.5) |
| `router vrrp <1-255> <IFNAME>` mode | 14 commands: `advertisement-interval, alternate-checksum-mode, circuit-failover, disable, do, enable, exit, help, no, preempt-mode, priority, show, transition-mode, virtual-ip`. **No `accept-mode`** (that is `router ipv6 vrrp`), and `vrrp vmac` is **global**, not router-mode |
| `virtual-ip <A.B.C.D> {master\|backup}` | `master` = this router owns the address; `backup` = it does not. With neither router owning it there is no preferred master and the election is pure priority |
| defaults | priority **100** (range 1-255), preempt **TRUE** with delay-time 0, advertisement interval **100 cs**, **`VMAC enabled`**, **`Accept mode: TRUE`** (the guide attributes accept-mode-on specifically to the AW+ **VRRPv3** implementation) |
| master-down | ~3 × the advertisement interval |
| interface down | the instance moves to **`Initialize`**, as the guide says |
| `transition-mode true` | every advertisement period emits **a v2 AND a v3 frame, ~26 µs apart**, from the same virtual MAC to the same group; v2 is 20 bytes of VRRP against v3's 12 and renders the same 1 s as `intvl 1s` rather than `intvl 100cs`. The peer is unaffected |
| 🔥 ordering | **`circuit-failover` and `transition-mode` are REFUSED while the session is enabled**: `% You must disable this session first`. Use `disable` → command → `enable`. `priority`, `virtual-ip` and `preempt-mode` do not need it |
| `circuit-failover <IFNAME> <delta>` | decrements the priority cumulatively while the monitored interface is down; up to 32 interfaces. It is the right failover stimulus — pick a monitored interface that is NOT on the measurement path |
| reboot | the instance, its virtual MAC, the election result and the monitored circuit all survive a cold boot, proven in the dataplane |

🔥 **How to grade "which router is master" when both share one virtual MAC.** The ARP reply, the
Ethernet addresses and the IP header are identical whichever router answers, so nothing at
layer 2 or 3 distinguishes them. Two things do:
- the **IP source of the advertisement** (each router's own interface address);
- the **TTL of a forwarded frame**, if the topology makes the two masters differ in hop count.
  On tb277 both host NICs land on the DUT, so giving the partner a static route back through the
  DUT makes a partner-mastered frame hairpin: **TTL 63 = the DUT forwarded, TTL 62 = the partner
  did**, in the same capture as an instrument flow pinned at 63. `tools/arpleg.py --show-ttl` and
  the per-spec `%L2DST` suffix exist for exactly this.

### 7C.3 🔴 The default VRRPv3-for-IPv4 checksum, and the two-master trap

With `alternate-checksum-mode` set on **one** router only, a single capture holds both routers'
advertisements and one decodes clean while the other reads `(bad vrrp cksum …)`:

| sender | mode | the DUT's own tcpdump |
| --- | --- | --- |
| DUT 10.38.22.34 | `alternate-checksum-mode` | **no complaint** |
| partner 10.38.22.35 | default | `(bad vrrp cksum 4a46)` |

Confirmed a third way: under `transition-mode true` the same daemon's **v2** frame validates
clean and its **v3** frame 26 µs later does not, so the decoder is not simply broken for VRRP.

**And the modes are mutually incompatible.** Mismatched, the partner stopped accepting the DUT's
advertisements and became master **at priority 100 against the DUT's 150** — two masters for one
virtual IP, both advertising from the same virtual MAC, and **ten** ARP replies to five requests.
Matched (either way) the pair re-converges at once, and default-to-default is provably fine: the
backup stays Backup *and* reports the master's address, which it can only learn by accepting the
frames.

⇒ **Set `alternate-checksum-mode` on every router in a virtual router or on none.** A staged
upgrade that sets it on one silently yields a split master. The VRRP Feature Overview Guide
(C613-22049-00 REV E) contains **zero** occurrences of "alternate" or "checksum" and warns of
nothing; the DUT's own help for the command is bare `<cr>`.

**Open, and deliberately not settled by that bench:** which mode is RFC 5798 §5.2.8-conformant.
RFC 5798 requires the VRRPv3-over-IPv4 checksum to cover a pseudo-header, and the obvious reading
is that the validator implements it and the default does not — but that rests on the validator
being right, which was not independently verified. The assumption-free statement is that **two
components of one firmware image disagree about the checksum of its own default VRRPv3
advertisement, and the vendor ships a command that makes them agree.** Whether a third-party
conformant VRRPv3 router would discard them is **NOT MEASURED**; the instrument needed is a
third-party conformant peer. Wants a developer.

### 7C.4 `no interface vlanN` is not universally allowed

`no interface vlan10` was **refused** on the x960-28YSQ with `% Removal of interface not
allowed` once the SVI had no address and no member ports — there was nothing left to remove, and
`vlan database` / `no vlan N` finished the job. The same command SUCCEEDED on an x950 GEN2 in
group C. A restore recipe must gate on the output; `cfg.py` stops at the `% ` and the teardown

### 7C.5 O-24's discriminator, both halves from one command

`no service <proto>` leaves a sticky config line **only on a unit that BOOTED with the service**
(§7A.2). Group D produced both halves in one operation: `no service vrrp` sent to two devices in

## 7D. IPv4 multicast — PIM-SM, PIM-DM, PIM-SSM and multicast VRF-Lite, measured 2026-10-16 (group C)

Four cases on `sin_x96056-20261012-24`, all PASS, every verdict carried by counted frames with a
never-joined control in the same leg. The `show` reads below are corroboration, never the proof.

### 7D.1 🔥 This bench CAN do two-router multicast — but only with swi_a

`service pim` **and** `service pdm` on the **-28YSQ** both answer
`% Service is not currently licensed on this platform`: its Base licence has no `PIM` bit.
`L3-MC-ROUTE` is **not** the PIM gate — all three units hold it, including the one that cannot
run PIM. The **x950 GEN2** partner runs both. The surface probe cannot settle this (§7D.2).

The topology that works, with both host NICs on the DUT: put the receiver's port in a VLAN the
**DUT has no SVI for**, trunk that VLAN to the partner, give the **partner** the SVI, and add a
transit VLAN between them. Read the transit with the DUT's own `tcpdump`.

### 7D.2 🔥 `service ?` does not reflect licensing — only `service <x>` does

`service ?` lists `pim`, `pdm` and `pim6` identically on a unit that can run none of them. A
read-only help probe can therefore **never** answer a licence question; issue the command and
read the refusal. A whole group's partner selection turned on this one accept/reject.

### 7D.3 🔥 `ip pim sparse-mode` does NOT enable router-side IGMP, and snooping hides it

The receiver interface needs an explicit **`ip igmp`** as well. Without it, IGMP **snooping**
still puts the group in `show ip igmp groups` with a live timer while
`show ip pim sparse-mode local-members` is empty and **nothing forwards** — two read-backs
disagree and the dataplane follows the pessimistic one. Confirm the report is well-formed on the
wire before blaming the platform (it was).

**Addendum, and it bites even when you know the rule:** a membership learned while the interface
was **snoop-only does not migrate** when `ip igmp` is later enabled — it must be re-sent.
Measured: first forwarding leg 0/10, identical leg after a re-join 10/10, nothing else changed,
because the baseline join preceded the `ip igmp` line by 45 s. **Apply the feature config before
the stimulus, not after.**

### 7D.4 🔴 The IGMPv2 any-source-join rejection is bound to hardcoded 232/8 ONLY

A v2 (*,G) join inside the IANA SSM range is rejected — **and that rejection persists with no
SSM configuration at all**, so `ip pim ssm default` is not what enforces it. A range configured
with `ip pim ssm range <acl>` gets **no such protection**: one `show ip igmp groups` showed
`239.20.20.20` (inside the configured range) accepted and `232.7.7.7` rejected, 40 s apart on
one interface. RFC 4607 §4.2 expects the configured range to carry SSM semantics too.
**Impact is bounded**: the wrongly-accepted membership is inert (0/10, no RP), so it is a
conformance gap, not a forwarding hole.

### 7D.5 Reading the tables: what tells SSM, ASM and DM apart

| signature | meaning |
| --- | --- |
| `Expires: stopped` + a real `Last Reporter` | SSM (S,G) include-mode state |
| a running group timer + `Last Reporter 0.0.0.0` | ordinary (*,G) membership |
| `(*,G) 0`, `(S,G) 1`, `(S,G,rpt) 0`, `SPT bit: 1`, no RP | pure SSM |
| `PIMv2, Register` / `Register-Stop` on the transit | PIM-SM, and only PIM-SM |
| `PIMv2, Prune Refresh` (State Refresh) + `Join / Prune` | PIM-DM, and only PIM-DM |
| `Graft` unicast + `Graft Acknowledgement` | PIM-DM re-attaching a pruned branch |

⚠️ **Do not read an (S,G,rpt) row's `RP: 0.0.0.0` as a missing global RP mapping.** That field is
empty on an `RPT NOT JOINED` entry whatever the global mapping is; read
`show ip pim sparse-mode rp mapping` for that. Misreading it once sent a wrong diagnosis to a
tester mid-case.

### 7D.6 🔥 A capture on any switched VLAN competes with a 1 Hz LDF stream

`loop-protection loop-detect ldf-interval 1 fast-block` is in this bench's baseline, so a short
`-c` budget is consumed by loop-detection frames before the traffic of interest arrives. Those
frames are **802.3/LLC with no IP header**, so a bare `ip` qualifier drops every one while
keeping PIM, IGMP and the multicast data:

```
tcpdump -i vlanN -c 30 -nn ip        # keeps PIM + data, drops LDF
tcpdump -i vlanN -c 7  -nn proto 103 # PIM control only (excludes the data)
```

### 7D.7 Multicast VRF-Lite

Genuinely per-VRF, with the **global table off throughout** (`no ip multicast-routing`):
`ip multicast-routing vrf <name>`, `ip pim vrf <name> rp-address <a>`, and a **per-VRF register
interface** (`pimreg<n>`, not the global `pimreg`) — that last one is good evidence the PIM
instance is VRF-scoped rather than one instance with VRF-tagged entries. Each VRF gets its own
loopback.

- Isolation measured source-in-red / receiver-in-blue: **0/10 multicast and 0/10 unicast**, the
  capture proved live by the DUT's own blue-SVI PIM hello. A/B closed by moving **one** interface
  into `red`: 0/10 → 10/10.
- **F-9's shape does NOT occur here** — the OIF empties with the interface and nothing stale
  forwards. That 10-15 finding is specific to the **unicast** inter-VRF path.
- An interface **cannot be moved between VRFs in one command**: `ip vrf forwarding <new>` answers
  `% <if>: VRF is already associated`; remove the old binding first, which silently drops the
  interface's IP addresses (`% All IP addresses configured on interface … removed` — an
  advisory, not a failure).
- ⚠️ **Bare `show ip mroute` enumerates every VRF**, printing `[VRF: red]` headers. It is not
  "the global table", and reading it as such makes VRF isolation look broken.

### 7D.8 `ip pim ssm` has an asymmetric negation

`ip pim ssm default` is accepted, but **`no ip pim ssm default` is `% Invalid input`** — the
removal form is bare `no ip pim ssm`. Same family as §7A's and §7C's negation traps: never assume
`no <exact command>` works, and probe with `?` **without a trailing CR**.

### 7D.9 Declared gap: the FLOOD half of flood-and-prune is NOT MEASURED

At 4–5 frames/s no data frame of any never-joined group reached the transit segment or the
receiver, with a capture armed beforehand in two of three attempts. State Refresh is active and
that is exactly what suppresses re-flooding, and the first-packet flood converges faster than a
0.2 s inter-frame gap can sample. **The prune is not in doubt — you cannot prune what was never
flooded — but the flood itself was not seen.** Measuring it needs a line-rate stimulus with
per-frame timestamps on the transit VLAN.

## 7E. AAA and RADIUS — measured 2026-10-20 (group A, aaa-2026-10-20T0825)

Measured on swi_d (AT-x960-56YSQ, `sin_x96056-20261012-24`) with a pure-Python RADIUS server,
client and pcap decoder (`tools/radsrv.py`, `tools/radsend.py`, `tools/radwire.py`) and a
console login driver (`tools/conlogin.py`). Cases T33407 (Local RADIUS Server) and T33408
(RADIUS client mode), neither of which has any authored step text.

### 7E.1 🔴 `local` at the end of a method list is a fallback for an UNREACHABLE server, NOT for a Reject

With `aaa authentication login default group radius local` and a RADIUS server that **answers**
`Access-Reject`, the DUT honours the Reject and never consults the local database. The console
prints `Login incorrect`. This cost a console login during T33408 and is the single most
dangerous fact in this area:

> **The moment the login method list points at RADIUS, every account you still need must exist
> on the RADIUS server, or you lose the console.** Writing `local` at the end does not protect
> you.

The fallback DOES engage when the server is unreachable — measured at **25.5 s** against 0.4 s
for the same credentials under a plain `local` list, i.e. `Timeout 5 sec` x (1 + `Retransmit
Count 3`) = 20 s plus overhead. Two consequences:
- a console-login tool's settle timeout must exceed 25.5 s or a successful fallback reads as a
  TIMEOUT (`conlogin.py --settle`);
- recovery from 7E.1 needs no reload: **stop the RADIUS server** and the local fallback works.

### 7E.2 🔥 `Last login:` in the console banner says WHO authenticated the login

A login served by the local database prints `Last login: <date> on ttyS0` before the
`AlliedWare Plus (TM)` banner. A login served by RADIUS prints **no `Last login:` line at
all** — the line comes from the Linux lastlog of a local account, and a RADIUS-authenticated
session has none. Measured across 5 local and 3 RADIUS logins in one case, every one matched
against the server's own Access-Accept lines, no exceptions. It is a discriminator available
**on the DUT console alone**, which no `show` command offers.

### 7E.3 An Access-Accept with no authorization attribute is accepted and then thrown away

An Accept carrying only a Reply-Message authenticated fine and then failed to build a session:

    awplus login: radclient1
    Password:
    login:
    Session setup problem, abort.

with `authpriv.err login: Invalid user name "radclient1". Abort.` and
`serial-getty@ttyS0.service: Main process exited, code=exited, status=1/FAILURE` in the DUT
log, while the server log showed a clean `Access-Accept`. Adding **`Service-Type =
Administrative (6)`** and the Cisco-style VSA **`shell:priv-lvl=15`** to the Accept made the
identical login succeed. The console message names none of this, so do not read
"Session setup problem" as an authentication failure.

### 7E.4 What the DUT puts in its own Access-Request, and what the `show` commands do not give

The x960 NAS sends: `Message-Authenticator`, `User-Name`, PAP `User-Password`,
`NAS-Identifier='console'`, a per-session `NAS-Port`, `NAS-Port-Type=5` and
**`Service-Type = 8 (Authenticate-Only)`**. It does **not** send `NAS-IP-Address`.
Accounting pairs correctly: Start on login, Stop on logout with `Acct-Session-Time` and the
same `Acct-Session-Id`, `Acct-Authentic=1`. A session opened before accounting was enabled
still produces a Stop.

- `show radius statistics` prints **nothing at all** on this build — client-side counting has
  to come from the server or the wire.
- `show radius server` is `% Incomplete command.`; the server table is in plain `show radius`,
  whose `Auth Status` / `Acct Status` go `Unknown` -> `Alive` after the first exchange.
- A shared-key mismatch and a dead server are **indistinguishable** in the DUT's log: both say
  `pam_radius_auth: RADIUS server <ip> failed to respond`. By design — a server that cannot
  verify a Message-Authenticator discards the packet silently (RFC 3579).

### 7E.5 The Local RADIUS Server is freeradius, and it serves PAP although `authentication ?` never says so

`radius-server local` + `server enable` starts `radiusd` on UDP/1812.
- `authentication ?` in config-radsrv offers only **eapmd5 | eaptls | mac | peap** — there is
  no `pap` keyword — yet plain PAP Access-Requests are served and answered correctly. All four
  listed methods are enabled by default, so `authentication mac` is a no-op that writes no
  running-config line.
- Enabling the server **auto-creates a `nas 127.0.0.1` entry** with a generated key and
  `message-authenticator optional`. It is not yours; `no radius-server local` removes it again.
- Keys and user passwords are stored and displayed **encrypted only**, in both running-config
  and `show radius local-server nas`.
- `show radius local-server` alone is `% Incomplete command.` — it needs a sub-command
  (`nas | user | statistics | …`).
- It logs a **BlastRADIUS** warning for every request from a NAS that sends no
  Message-Authenticator, and suggests `nas <ip> message-authenticator optional`.
- A request from a source that is not a configured `nas` is dropped with
  `Ignoring request to auth address * port 1812 … from unknown client <ip>`, and the
  **`Unknown NAS` counter does NOT increment** — the packet never reaches the counted path.
- With PAP, a **wrong shared key is counted as a Failed Login, not as `Shared key mismatch`**
  (which stayed 0): there is nothing in a PAP request for the server to validate the key
  against, so the password simply decodes to garbage.
- With the feature off, UDP/1812 answers **ICMP port-unreachable** — a stronger OFF baseline
  than silence.

### 7E.6 Console login lands at privilege 1

An AW+ console login reaches `awplus>` even for `username manager privilege 15`; `enable` then
raises it to 15. A login test's success criterion on this platform is reaching `>`, not `#`.

### 7E.8 RADIUS proxy — a real RADIUS hop, and three CLI traps

Measured in T33409 with deliberately DIFFERENT secrets on the two legs (NAS↔proxy
`testing123`, proxy↔upstream `testing456`) and one capture covering both.

- **The proxy terminates and re-originates.** The upstream request has a new RADIUS
  identifier, carries **`Proxy-State`** holding the original id (RFC 2865 §5.33), gains a
  **Message-Authenticator the NAS never sent**, and is signed with the upstream's key. Decoding
  the one pcap twice proves it: NAS leg valid=5/invalid=0 under `testing123`, upstream leg
  valid=5/invalid=0 under `testing456` and valid=0/**invalid=5** under `testing123`.
- 🔴 **`rule N realm <r> server <ip>` can only reach a server on the DEFAULT ports.** It
  resolves by IP + (1812,1813) and takes no port argument, so against a server configured on
  any other port it answers `% Server <ip> (1812,1813) is not configured` — even when that
  server is already in the running-config. **Use a `group`**: `group <name>` → `server <ip>
  auth-port <n> acct-port <n>`, then `rule N realm <r> group <name>`.
- ⚠️ **`nostrip` is a prefix of the target, not a suffix**: `rule N realm <r> nostrip group
  <g>`. The other order is `% Invalid input detected`.
- ⚠️ **A rule cannot be edited in place** — `% Rule 1 already exists`. `no rule N` first.
- 🔥 **An unmatched realm is still PROXIED, and is NOT stripped.** `rule N realm …` selects the
  upstream group and controls stripping; it does not decide whether a request is proxied.
  A username whose realm matches no rule goes upstream verbatim.
- **A wrong NAS-to-proxy key is not detected**: with PAP and no Message-Authenticator from the
  NAS, the proxy decrypts the password with its own key, gets garbage, re-encrypts it upstream,
  and the upstream answers "wrong password". A wrong key and a wrong password are
  indistinguishable.
- `no proxy enable` alone closes the listening socket (back to ICMP port-unreachable) while
  leaving the rest of the configuration; `no radius-server proxy-server` removes the block.
- The DUT's log attributes decisions explicitly: `Marking home server <ip> port <n> alive` and
  `Login incorrect (Home Server says so): [<user>]`.
- ⚠️ **Entering `group <name>` CREATES it**, so a `qmark --mode` probe of that sub-mode is not
  read-only. Clean it up, or do not probe it at TRIAGE.

### 7E.7 TACACS+ cannot be tested on a box where you are not root

`tacacs-server host <ip> ?` offers only `key | vrf | <cr>` — **no port option**. TACACS+ is
locked to TCP/49, so the server must bind a privileged port. RADIUS is testable without root
only because `radius-server host <ip>` takes `auth-port` and `acct-port`.

## 7F. Management — telnet, the default-password warning and triggers, measured 2026-10-20 (group C, mgmt-2026-10-20T0825)

`tools/tcpflow.py`, `tools/httpq.py` (all new) and `tools/snmpwire.py`. Cases T33378, T47199
and T33416, none of which has any authored step text.

### 7F.1 `service telnet ip` is stored as `service telnet` PLUS `no service telnet ipv6`

The running-config never contains `service telnet ip`. The three states read:

| state | `show telnet` Protocol | running-config |
| --- | --- | --- |
| off | `None` | `no service telnet` |
| IPv4 only | `IPv4` | `service telnet` **and** `no service telnet ipv6` |
| both | `IPv4,IPv6` | `service telnet` alone |
| IPv6 only | `IPv6` | `service telnet` **and** `no service telnet ip` |

A `show running-config | include telnet` therefore distinguishes the states by **which
negation is present**, not by a positive line. Grepping for `service telnet ip` finds nothing
on a device where IPv4 telnet is on.

### 7F.2 🔥 `show telnet` reads "Enabled" while IPv4 TCP/23 is REFUSED

With `service telnet ipv6` on and `no service telnet ip`, `show telnet` reads
`Telnet server : Enabled`, and at the same instant a TCP connection to port 23 on the DUT's
IPv4 SVI is answered by `RST.ACK`. This is the §5 family — a `show` reporting a feature
Enabled while the thing under test does nothing — and here it is CORRECT behaviour. The
consequence for grading is absolute: **"Telnet Server (IPv4)" can only be graded on the
wire.** A case graded from `show telnet` would pass with the IPv4 half switched off.

### 7F.3 `service telnet` prints a `% ` warning and SUCCEEDS

`% Warning: Telnet is insecure and deprecated. Please use SSH.` — an advisory, logged by the
device itself as `user.warning IMI[...]`. It stopped `cfg.py` at the very command that turns
the feature on until `Telnet is insecure and deprecated` was added to `console.ADVISORY`.

### 7F.4 🔴 A device still on the factory password `friend` gives NO warning, on any path

The subject of T47199, and the campaign's clearest product finding. On swi_d AND on swi_b —
different model, different build, both still authenticating `manager`/`friend` —
`% Default password needs to be changed.` appears on **no** access path: console (twice each),
telnet, SSH. No log line either.

- The authority says it should: **X960 TPS row 271** "Show warning message when user continue
  to use default PW" = **Yes**, and the feature's own TFS (project 2616, MRS-1071, approved
  Oct 2021) spec 2616.1 says the check runs *"at every login using the default account
  'manager'"*, with `Configuration Commands: None`, `Logging specifications: None`,
  `Initial Release Targets: all platforms in 5.5.1-2`, `Excluded Targets: None`.
- The absence is a measurement, not a blind spot: a `banner exec <marker>` was armed and the
  marker appeared on console, telnet and SSH **in exactly the position the TFS example puts
  the warning** — the last line before the first prompt.
- A second subsystem agrees. The current FDPC engineering page says a device in the
  "Factory-default password" state is held in HTTP **login-only mode** and its APIs answer
  403 with `API access requires admin password to be configured`. `GET /restconf/data` with
  `manager`/`friend` returned **200 OK, 11848 B of yang-data**. The DUT does not believe its
  password is the factory one.
- **The mechanism, from the product's own page:** *"Currently, we only check that the password
  has been encrypted with an MD5 hash, as the default-generated config contains this but a
  user-generated config will not."* Both units store it as **`$5$` (SHA-256-crypt)**, not
  `$1$` (MD5).
- Hash provenance is readable at a glance: both units' `manager` hashes carry an
  **8-character salt**; a password set through the CLI gets a **16-character salt**. Different
  generators.
- NOT closed: the FDPC `def_pwd_chg` U-Boot variable is unreadable without a reboot, and
  `default-password ?` / `show default-password ?` are both `% Unrecognized command`.

⚠️ Before changing `manager`'s password on a bench unit to test this: `security-password
minimum-length 8` makes the six-character `friend` unrestorable in plaintext, and
`security-password history 1` can refuse the return. Restore by the **encrypted** form, and
keep a second privileged account open first.

### 7F.5 The x960 Web GUI is a separate file, and tb277's DUT does not have one

`show http` → `Web GUI Information / GUI file in use : -`. The server is live (nginx, TLS on
443 with a self-signed `CN = AlliedwarePlusDefault` cert, `Content-Security-Policy` and
`X-Frame-Options` set) and every path answers **404**, with
`nginx: open() "/usr/html/public/login.html" failed` in the DUT log. So **there is no HTTP
login to observe** on a unit with no GUI loaded, and any case with an HTTP-login limb must
either load one (`activate flash:/Load-gui9.sh`, a bench change) or declare the limb
NOT MEASURABLE. RestCONF under `/restconf/data` works regardless.

### 7F.6 Triggers: `type interface` exists, and what the surface is

`type ?` inside `trigger <1-250>` offers fifteen types: `atmf cpu env-sensor interface
linkmon-probe log main-pse memory periodic ping-poll pse-port reboot stack time usb`.
`type interface <IFNAME> any|down|up|<cr>`.

- 🔥 **Entering `trigger N` and leaving without setting a `type` CREATES NOTHING** — nothing in
  `show trigger`, nothing in the running-config. So a read-only help probe of the trigger
  sub-mode is safe, and a TRIAGE can enumerate `type ?` without leaving state behind.
- `type` must still be set before `description` (`% Please specify the trigger type first`).
- ⚠️ **`show running-config | include trigger` prints only `trigger 1` / `trigger 2`** — the
  sub-mode lines (`type ...`, `description ...`, `trap`, `repeat forever`) do not contain the
  word, so the grep tells you a trigger exists and nothing about what it does. Use
  `show trigger <n>`.
- ⚠️ **`show trigger` with no triggers prints `% No triggers currently defined`** — a `% ` line
  from a SUCCESSFUL show, which stops `cfg.py`. Run shows through `ckcon.py`, not `cfg.py`.
  It is deliberately NOT in `console.ADVISORY`, which is for configuration commands.

### 7F.7 A trigger's SNMP trap is per-trigger, and it names the trigger

`snmp-server enable trap ?` lists 33 groups and **none of them is a trigger group**: the
per-trigger `trap` sub-command is self-contained. With `snmp-server community <c> ro` and
`snmp-server host <ip> version 2c <c>` alone, an activation sends:

    snmpTrapOID 1.3.6.1.6.3.1.1.4.1.0 = 1.3.6.1.4.1.207.8.4.4.4.53.0.1
    varbind     1.3.6.1.4.1.207.8.4.4.4.53.1.0 = INTEGER: <the trigger ID>

One trap per activation, from the configured source SVI to the configured host. The trigger ID
in the varbind is what lets two triggers on the same port be told apart on the wire.

### 7F.8 A trigger executes its action list, and says so in the log

    user.notice TRIGGER[1411]: Trigger 1 (ck down on port1.0.2) activated
    user.err    TRIGGER[1411]: Unable to activate script /flash/cktrig.scp (File not found)

Pointing `script 1` at a **deliberately non-existent** file is the cheap way to prove the
action list is executed rather than merely counted — the configuration is accepted (it is in
`console.ADVISORY`: *"does not exist. Please ensure it is created"*), and the activation then
logs the attempt. Running a real script still needs a `.scp` on the device's flash, which
needs a root write to the box's `/tftproot` (STANDING-ORDERS §4) — still unmeasured, as it was
after T44181.
