# x960 — platform facts (AT-x960-56YSQ and AT-x960-28YSQ)

**What this is.** The platform, firmware and CLI behaviour of the x960 family that has cost
hardware hours, been mistaken for a defect, or would otherwise be re-derived. Read it whenever
the DUT's family is x960 (`/orient-dt` §2). Unless a row says otherwise, everything measured
here was measured on **tb277**, on the build it names. What any bench *currently* is (cabling,
boot source today, which ports are cabled) is never written here: that is the box's generated
`bench-state.md`.

## 1. 🔥 The two models do NOT share a switching core

This is the single most load-bearing fact about the family, and it is invisible from the CLI.

| model | switch chip | family | note |
| --- | --- | --- | --- |
| **x960-56YSQ** | **Marvell 98CX8514** | **Falcon** | **no PHYs** — every port connects directly to the switch chip |
| x960-28YSQ | Marvell 98DX4580M | AlleyCat5P-XL | has MACsec support |

Source: TPS. The CPU on both is a Marvell CN9130 (Octeon family) multi-core ARMv8.

**Consequence, and the Test Strategy says it in as many words:** *"The Falcon switching core is
new to this family. Results from the x960-28YSQ demonstrate nothing about this board's
dataplane"* and *"ART on another platform proves nothing about this"*. So:

- A dataplane result from the -28 is **not** evidence about the -56, even though both report the
  same software version and the same `show` output.
- ART/CR history from other platforms (the `1336_acl` suite's CRs were raised on FS980 and
  GS970EMX) points at *where to look*, never at what this board does.
- There is **no reference platform** for Falcon in this project. The Test Strategy's instruction
  is to verify dataplane behaviour from first principles against the TPS limits.

Related: [[corpus-sources-are-not-authoritative]].

## 2. Falcon TCAM — the limit behind most "odd" ACL/QoS behaviour

From the TPS. The TCAM is shared between QoS, ACLs, tunnel terminations and subnet-based VLANs.

| | AC5P-XL (the -28) | **Falcon (the -56)** |
| --- | --- | --- |
| raw | 24K x 20-byte rules | 36K x 10-byte = 18K x 20-byte, **split over two control pipes** |
| usable 20-byte rules | 24K | **9K** |
| ACLs (60-byte rules) | 8K with an AC5P-XL-only silicon profile | **3K max**, if nothing else used the TCAM |

**The project works to a 2.5K 60-byte rule budget**, chosen as the lowest common denominator so
mixed stacking works. The Test Strategy lists *"TCAM consumption against the chosen 2.5K rule
budget on Falcon"* as a named risk, and calls out *"TCAM utilisation and contention with QoS"* as
a coverage area.

- 🔥 **MEASURED 2026-10-09 on tb277 (`sin_x96056-20260921-9`): the DUT reports an ingress
  classifier pool of `Total 2 / 1024`, i.e. 1024 entries — NOT the 2.5K–3K above.** Egress reads
  `0 / 6144`. Only `[Instance 0]` appears, covering `port1.0.1-port1.0.77`, where the TPS
  describes two control pipes. Whether 1024 is correct for this build is OPEN; if it is, the
  project's 2.5K rule budget needs restating. Three further measurements, same session:
  - **one bound rule = exactly one ingress entry** (five lists bound at once read `ACL 5`);
  - **an UNBOUND access-list costs NOTHING** — six defined with one bound reads `ACL 1`, so the
    budget is spent per **binding**, not per definition;
  - **the SAME rule costs 1 entry via `access-group` but 3 via `service-policy input`**
    (`QoS 3`). A QoS-bound ACL is three times as expensive as the identical interface-bound one.
- **Check it with `show platform classifier statistics utilization brief`** (ACL guide p18).
- **🔥 MEASURED 2026-10-08 on `sin_x96056-20260921-9` (T44992), and it contradicts the TPS
  arithmetic.** The ingress pool is **1024 entries**, not the ~3K the TPS implies, and the cost
  per rule depends on how the ACL is applied:

  | state | counters | total |
  | --- | --- | --- |
  | clean DUT | `Loop Detection 2`, all else 0 | `2 / 1024` |
  | one hardware ACL rule via `access-group` on `sa1` | `ACL 1` | `3 / 1024` |
  | the SAME rule via `service-policy input` on `sa1` | `ACL 0`, **`QoS 3`** | `5 / 1024` |

  ⇒ **one rule = 1 entry through `access-group`, but 3 entries through the QoS path.** Ceiling on
  this build is therefore ~1022 rules via access-group and ~340 via service-policy, before any
  other feature takes its share. The pool is shared with Global ACL, VACL, QoS, Loop Detection,
  EPSR, CFM, G8032, DoS, RA Guard, BFD/BEFD, AMFAPPS, IPFIX (Flow + Sample), OpenFlow
  (Hybrid/Flow/Default) and MLAG, each separately counted. Egress is a separate `0 / 6144`.
  The project budget is **2.5K 60-byte rules** and the Test Strategy's headline risk is
  *"TCAM consumption against the chosen 2.5K rule budget on Falcon"*. Raised to the Test
  Engineer 2026-10-08 as a candidate CR in its own right; unanswered.
- **`mls qos enable` prompts and briefly interrupts traffic**: `Traffic will stop while
  configuration is applied. Continue? (y/n):` — answer `y\r`
  ([[awplus-config-prompts-abort-and-logout]]). Because it stops traffic, a control measurement
  taken before QoS was enabled does not carry across it; take a fresh one after.
- When an ACL is accepted but does not take effect, or a QoS policy displaces one, suspect TCAM
  exhaustion before suspecting the feature. The two-pipe split is its own hazard: rules are not
  one flat pool.

## 3. MACsec and flow control are NOT supported on the -56

- **MACsec: not supported on the x960-56YSQ** — the Falcon chip does not have it (TPS). On the
  **-28** it is supported, but **not on ports 17–24** (silicon: MACsec covers only the first two
  DMA groups, lanes 0–15), and on ports 25/29/33/37 it is handled by the 100G uplink PHY and
  works only from 5.5.6-2 onward.
- **Flow Control: `No` — *"Cannot be supported due to a silicon issue"*** (TPS row 155).
  This is what a real platform limit looks like in the TPS, and it is the evidence an
  UNSUPPORTED verdict should cite. Compare [[stack-refused-command-lands-on-backups]]: on a
  stack a refused `flowcontrol` still landed on the backups.

## 5. ACL and mirroring CLI — measured and documented

Measured on tb277 (`sin_x96056-20260921-9`) 2026-10-07/08, cross-checked against the guides.

- **Hardware ACL actions** (ACL guide Table 2, p13) — the definitions a verdict is graded
  against: `copy-to-cpu` = copy to CPU **and forward**; `send-to-cpu` = to CPU and **not**
  forwarded; `copy-to-mirror` = copy to mirror port **and forward**; `send-to-mirror` = to the
  mirror port, **not switched**; `deny-and-not-cpu` = drop without reaching the CPU.
  - ⚠ **A bound NUMBERED hardware ACL cannot be edited; a bound NAMED one can.** Measured
    2026-10-09 (T44987). With `access-group 3000` on a port, `access-list 3000 deny ...` is
    **refused**: `% This access-list is currently attached to an interface so cannot be edited.`
    — the entry is not added. The named sub-mode behaves oppositely: re-entering
    `access-list hardware <name>` prints an **advisory** and the edit succeeds on `exit`/`end`.
    ⇒ to change a numbered list, remove the `access-group` first, edit, then re-apply.
    🔥 **The two `%` strings differ by one word and mean opposite things**
    (`is attached` = advisory, `is currently attached` = rejection). `tools/test_advisory.py`
    pins the pair; never loosen the advisory pattern to span both.
  - ⚠ **The guide's table is generic AW+ ("depending on your switch family") and this build
    offers only SIX of them.** Measured 2026-10-08 on `sin_x96056-20260921-9`:
    `access-list 3000 ?` and `access-list 4000 ?` both offer exactly
    `copy-to-cpu  copy-to-mirror  deny  permit  send-to-cpu  send-to-vlan-port`.
    **`send-to-mirror` and `deny-and-not-cpu` are absent** from the numbered forms. Whether they
    exist inside the `access-list hardware <name>` sub-mode is **not yet confirmed** — reaching
    that sub-mode creates the list, which a read-only triage would not do.
  - `copy-to-mirror` additionally takes `interface <port>` ("Mirror interface to send to"), so a
    mirror destination can be named explicitly instead of relying on `mirror interface none`.
  - `send-to-vlan-port` is present, and the TPS marks it supported.
  - ⚠ `send-to-cpu` lands traffic on a CPU queue that *"could result in EPSR healthcheck
    messages and other control packets being dropped"* (guide), and T44989's own precondition
    cites **CR30477** for STP/EPSR interference. Two independent sources. Watch STP state across
    any send-to-cpu case.
- **`access-group` is for ports and aggregators.** Per-VLAN ACLs use a different mechanism
  entirely — `vlan access-map` + `match access-group` + `vlan filter <map> vlan-list <list>
  input` (guide p17). **An absent `access-group` under `interface vlanN` is correct, not a
  defect** — a 2026-10-07 session recorded the opposite inference and it was wrong.
  Measured 2026-10-08: under `interface vlan1`, `access-group`, `service-policy` **and**
  `static-channel-group` all return `% Unrecognized command`, while `vlan access-map WORD` and
  `vlan filter <map> vlan-list` both parse in global config. Both halves now measured.
- **The ingress classifier pool reads 1024 entries**, not the ~3K the TPS's Falcon arithmetic
  implies (measured 2026-10-08, clean DUT: `show platform classifier statistics utilization
  brief` → `Total 2 / 1024`, the 2 being Loop Detection; egress `0 / 6144`). The same pool is
  shared by System, DHCP Snooping, Loop Detection, EPSR, CFM, G8032, Global ACL, ACL, VACL and
  QoS, each separately counted — which makes the Test Strategy's ACL-vs-QoS contention directly
  measurable. **Only `[Instance 0]` is reported, covering `port1.0.1-port1.0.77`**, though the
  TPS describes Falcon as split over two control pipes. Open question against the project's
  2.5K 60-byte rule budget — raised to the Test Engineer 2026-10-08, not yet answered.
- **Apply to a static channel group on the aggregator itself**, not its members; for an LACP
  channel group, apply to every member port (guide, IPv4 hw ACL introduction).
- **Hardware ACLs implicitly PERMIT** what no rule denies; software/standard ACLs implicitly
  DENY. Opposite defaults, easy to grade the wrong way round.
- **Interface ACLs are matched BEFORE QoS policies on the same port** (guide p24). A permit in
  the interface ACL forwards the packet and **bypasses every subsequent QoS rule**. ⇒ when a
  case says "apply the same ACL via service policy and repeat", the `access-group` must be
  removed and proven gone first, or the QoS path is never exercised and the result is a false
  pass. The QoS path is `mls qos enable` → `class-map` `match access-group` → `policy-map`
  `class` → `service-policy input` (guide p24–25); `mls qos enable` prompts (y/n) —
  [[awplus-config-prompts-abort-and-logout]].
- ⚠ Do **not** enable `access-list hardware-deny-log` while any `copy-to-cpu`/`send-to-cpu` ACL
  exists: matching packets are then dropped (guide p14).
- **🔥 `show access-list counters` DOES NOT INCREMENT on the service-policy path.** Measured
  2026-10-08 (T44992): with the ACL bound by `access-group`, Packet Hits tracked the traffic
  exactly (4 pings → 4 hits). With the SAME ACL bound through `class-map` → `policy-map` →
  `service-policy input`, the deny was **demonstrably enforced** (100% loss) while Packet Hits
  stayed at **0**. ⇒ **never use ACL hit counters as the evidence for a QoS-bound ACL** — a
  working rule reads as a dead one. Use the traffic result, and the `QoS` row of
  `show platform classifier statistics utilization brief`, instead. Whether this is intended or a
  defect is open; it is a candidate CR.
- `no mls qos enable` is rejected (`% Invalid input detected at '^' marker.`); the negation is
  **`no mls qos`**. Note the asymmetry: `mls qos enable` prompts (y/n), `no mls qos` does not.
- **`copy <file> flash:/default.cfg` is refused** — `% Cannot overwrite flash:/default.cfg as it
  is the default config file`. A saved baseline therefore cannot be restored by copying it back
  over the active boot config. Restore by tearing the running-config down and re-saving with
  `copy running-config startup-config`; never `delete flash:/default.cfg` on a netbooting unit,
  which leaves a window with no startup config at all.
- **HOST trap:** Linux drops a secondary address from the testbox NIC when the link bounces —
  `10.38.22.66/27` vanished from `eth4` during the DUT's reload. Re-add any secondary address
  after a reload before using it as a traffic control (measured 2026-10-08).
- **A standard (1–99) list cannot be bound to an interface** on this platform (measured
  2026-10-07); `access-group` takes 3000–3699, 4000–4699 or a named hardware list. Standard
  lists still bind to `vty access-class` (guide p16).
- **Mirroring** (guide p3–4, 6, 14): **one mirror destination per switch**, local or remote. The
  destination port leaves every VLAN and **stops participating in normal switching**, so it must
  be removed from trunks and VLANs first, and it must not be an STP-discarding port. The command
  is entered on the **destination** port naming the **source** (`mirror interface <src> direction
  transmit|receive|both`), which is why `show mirror interface <X>` keys on the **monitored**
  port. `mirror interface none` makes the port an **ACL-driven** destination for
  `copy-to-mirror`/`send-to-mirror` — it is not an off switch, and `show mirror` then reports
  `none (via ACL)`. `copy-to-mirror` **terminates ACL processing at the first match**, which is
  why `mirror interface <src> vlan <vid>` was added later.
- **Two `%` lines on this platform are ADVISORIES, not rejections.** The command succeeds and the
  prompt advances, but a `% `-matching stop-on-error driver aborts on either
  ([[bench-scripts-stop-on-cli-errors]]). Measured 2026-10-07/08:
  - `% <port> is currently configured as a mirror-port...`
  - `% This access-list is attached to an interface. The modified configuration will be applied
    to the interface automatically after exiting this configuration mode by entering "exit" or
    "end" command.` — re-entering `access-list hardware <name>` while it is bound to an
    interface. Note what it also tells you: **edits to a bound hardware ACL do not take effect
    until you leave the sub-mode**, so a counter read before `exit`/`end` reflects the OLD rule.
- **The named hardware ACL sub-mode offers `mac` where the numbered IP form does not.** Measured
  2026-10-08 in `(config-ip-hw-acl)`: `deny ?` → `icmp ip mac proto tcp udp`, against the
  numbered `access-list 3000 deny ?` → `icmp ip proto tcp udp`. (Closes triage issue I-8.)
- **Hardware ACLs are INGRESS.** `access-group` on a port or aggregator filters what arrives on
  it. An ACL on `saN` therefore never sees a flow that merely egresses `saN` — write the rule for
  the direction that ingresses the bound interface, and source the traffic accordingly, or it
  cannot match and the zero counter reads like non-enforcement.
- 🔥 **Mirror status output does NOT describe the dataplane. Measured 2026-10-09 on tb277,
  `sin_x96056-20260921-9`, all three proven by frame capture at the destination:**
  1. **`direction both` copies NO frames at all**, while `show mirror`, `show mirror interface
     <src>` and the running-config all report it correctly, and it survives a save and reload.
     Proven on a pristine boot (saved to flash, DUT reloaded, so no re-application history could
     be blamed), where `transmit` and `receive` applied on that same boot each delivered their
     frames. Reproduced 5x. **FAIL-grade defect**, case T44969.
  2. **A RE-APPLIED mirror copies nothing until the destination port is bounced**
     (`shutdown` / `no shutdown`). Only the first-ever mirror on a port works immediately.
  3. **An in-place `direction` change is SILENTLY IGNORED** — no error, and `show mirror` keeps
     reporting the OLD direction, which the dataplane also keeps using. `no mirror interface
     <src>` must come first.

  ⇒ **Never grade a mirroring case from `show mirror`.** Remove → apply → bounce the destination
  → then capture frames. Five mirroring cases would have passed on a status read-back alone.
- `show interface status` reports a mirror destination port identically with and without a
  mirror, so it cannot evidence "returned to normal switching". **A capture can:** measured
  2026-10-08 (T44973), the moment the mirror is removed the destination port starts carrying
  normal traffic again and the host NIC sees LLDP and VLAN-1 broadcast. That is the only
  available proof for that step.
- `clock set` is exec-only (no running-config footprint); `clock timezone` is config-mode.

### 🔥 Port mirroring: three defects, and why `show mirror` cannot be trusted

Measured 2026-10-08/09 on `sin_x96056-20260921-9` (campaign `mirror-2026-10-08T1637`, cases
T44967–T44974). All three are reproducible, none is in any case's step text, and **none of them
is visible from the CLI** — in every one, `show mirror` reports the mirror `Enabled` with the
right direction and source while the dataplane does something else.

| | defect | what the CLI shows |
| --- | --- | --- |
| **M1** | A **re-applied** mirror copies nothing until the destination port is bounced (`shutdown` / `no shutdown`). Only the first mirror ever applied to a port works immediately. | `Enabled`, correct direction |
| **M2** | An **in-place `direction` change** over an existing mirror is accepted with no error and is silently discarded. The dataplane keeps the old direction too. `no mirror interface <src>` must come first. | the **stale** direction |
| **M3** | **`direction both` copies NO frames at all**, and survives a save and reload in that state. | `Enabled`, `direction both` |

The discriminator for M3, one boot, one cabling, one 6-ping flow, same procedure — and the
capture sizes are the evidence, 1 byte meaning nothing arrived:

| direction | capture | echo requests | echo replies |
| --- | --- | --- | --- |
| `transmit` | 535 B | 0 | 6 ✅ |
| `receive` | 547 B | 6 | 0 ✅ |
| **`both`** | **1 B** | **0** | **0** ❌ |

M1 was ruled out as the cause of M3 by using a reload: `both` was saved to startup and the DUT
rebooted, so on that boot there was no re-application history at all, and it still copied
nothing — while `transmit` and `receive` applied on that same boot both worked. Also ruled out
before grading: settle time, a second destination bounce, link state at both ends, host capture
(`tcpdump` reported `0 packets received by filter` on an unfiltered run) and a wedged mirror
engine (re-applying `transmit` mid-session worked at once).

**⇒ Never accept `show mirror` as proof that mirroring works on this platform.** Every mirror
verdict needs frame-level capture at the destination. A test that reads back `show mirror` and
stops there records a pass on all three of these. The working method that does hold:
`no mirror interface <src>` → apply → **bounce the destination** → only then measure.

Evidence: `tb277/x960/mirror-2026-10-08T1637/` — T44969's log for M3, T44968's for M1 and M2,
plus `work-box/` for the raw captures. CR wording was left to the Test Engineer; these are
measurements, not graded product judgements.

## 6. DHCP server, DHCP relay and DNS relay — measured 2026-10-15

Measured on tb277, **AT-x960-56YSQ S/N A2WQS700B, `sin_x96056-20261012-24`**, six AWPTCM cases
(`tb277/x960/dhcp-*-2026-10-15T1458/`), all PASS. Each item below would otherwise produce a
confidently wrong verdict next time.

### 6.1 🔥 A relayed DHCP frame is INVISIBLE to scapy unless BOOTP is bound on dport alone

An AW+ relay forwards the client frame from an **ephemeral source port**, not from 67. scapy's
default binding is on the source port, so a sniffer that does not rebind decodes **nothing** —
and the run reads as *the relay is dropping every packet*. Before reading any relayed capture:

```python
bind_layers(UDP, BOOTP, dport=67); bind_layers(UDP, BOOTP, dport=68)
```

Measured: a scapy server received 0 frames, then 5, after those two lines and no other change.
`tools/dhcp4.py` and `tools/opt82dump.py` both carry the fix.

### 6.2 `ip dhcp-relay agent-option checking` validates SERVER RESPONSES, not client ingress

The name reads like an untrusted-ingress check. It is not: it polices what comes **back** from
the server. Measuring it on the ingress side proves nothing, and a case designed around
"the relay should drop a client frame that already carries option 82" tests the wrong direction.
The ingress behaviour is `ip dhcp-relay information policy` instead (replace / keep / drop /
append), and all four were measured correct.

### 6.3 `probe type ping` ARPs FIRST — "no ARP" does not discriminate the two probe types

For a locally connected client the ping probe sends ARP before it sends ICMP, then escalates.
So the presence or absence of ARP frames cannot tell `probe type arp` from `probe type ping`.
Discriminate on the ICMP echo instead. Related: under `probe type ping`, an ARP reply **alone**
does not withhold the address — only the ICMP echo reply does — which is narrower than the
literal "or" in the ARP Probe TFS S1566.1.01.

### 6.4 ⚠️ Two near-identical `% …already…` messages mean OPPOSITE things

| message | meaning | state |
| --- | --- | --- |
| `% DHCP Relay is already globally enabled` | **advisory** | the state holds; carry on |
| `% DHCP client is already running on this interface.` | **genuine rejection**, exit 2 | the config was NOT applied |

Measuring past the second one captures the **default** DHCP client and reports it as the
configured one. A gate that treats every `%` line as fatal is also wrong here: `% Can not
configure DHCP Relay agent option remote-id unless agent option is set` is the *expected* result
of a negative step.

### 6.5 All SVIs share ONE MAC, so option 61 cannot identify which interface was named

`vlan1`, `vlan10` and `vlan48` all read `e01a.ead4.7043`, so `ip address dhcp client-id vlan10`
and `... client-id vlan48` emit **byte-identical** option 61. Grade such a case on presence, type
byte and length, and say so; a content comparison proves nothing. Check
`show running-config interface vlanN` for the keyword before capturing.

### 6.6 The DHCP client's parameter request list is [1,3,15,6,43]

Option **43** is additional to what the wiki DHCP page documents (1/3/6/15). Not a defect;
expect it, and expect `request vendor-identifying-specific` to append **125** to that list.
`vendor-identifying-class` emits option 124 carrying IANA enterprise **207** (Allied Telesis).

### 6.7 A DHCP-learned DNS server is queried in PREFERENCE to a statically configured one

Measured with two responders on one NIC answering different A records: the relay queried the
DHCP-learned `.2` and **never ARPed** for the static `.9`; a control with `.9` alone proves `.9`
is reachable and used. DNS Relay TFS S1570.1.12 says DHCP-learned servers are "added **last**",
which describes list position — a resolver need not walk its list in order, so this is an
observation, not a defect. **`show ip name-server` cannot settle it either**: its display is
type-grouped, and it lists the dynamic entry first regardless of configuration order.

### 6.8 🔴 Any DNS or DHCP-client change restarts the relay process — wait 20 s before counting

Documented in the DNS Relay TFS "Limitations"; measured here. A leg run ~3 s after such a change
forwarded **nothing** and read as *the DUT cannot use a statically configured DNS server*. The
identical configuration after a 20 s settle forwarded every query and ARPed for the server first.

### 6.9 Open: is the DNS forwarding cache meant to cover RELAYED queries?

With `ip dns forwarding cache size 100 time 60` and `DNS Cache: enabled, Size 100, Max-TTL 60`,
two identical queries 5.3 s apart **both** went upstream. Not graded a failure: the TFS separates
a *Name Resolver Process* from a *DNS Relay Process*, and S1570.1.03/.11 both say "name **resolve
result**", which plausibly scopes the cache to the device's own lookups. Nothing on the bench
separates "not cached by design" from "cache broken". **This wants a developer's answer, not
another bench run.** Evidence: `tb277/x960/dhcp-client-2026-10-15T1458/T43854/T43854.log`.
