# x980 — platform facts (AT-x980-16CDQ)

**What this is.** The x980 behaviour that has cost bench time or would otherwise be re-derived.
Everything here was **measured** on **tb490**, swi_dut = AT-x980-16CDQ S/N A10732A263200035 with
XEM3-12YS (bay 1) and XEM3-8CQ (bay 2), build `awplus_main-20261029-90`, during campaign
`tb490/x980/CAMPAIGN-QUEUE-2026-10-29T1304.md` (group A, auth). What the bench currently is
lives in `bench-setup/tb490/bench-state.md`, never here. No TPS or Test Strategy page was read
for these rows. How to add to this file: [README.md](README.md). The x960 auth traps in
`platforms/x960.md` §7K were checked here where noted.

## 1. Authentication & Security — measured 2026-10-29

### 1.1 Web authentication: the command surface on this build
- `auth-web-server ?` offers dhcp, host-name, intercept-port, ip-conflict-prefer-newer-supplicant,
  ipaddress, login-url, page, ping-poll, port, redirect-delay-time, redirect-url, session-keep, ssl,
  trustpoint. There is **no `auth-web-server mode`** (`% Unrecognized command`) and **no
  `auth-web-server gateway`**. The intercept/promiscuous *modes* in the AW+ Tips and Tricks guide
  are not configurable here. Interception is built in: an unauthenticated client's TCP 80 to ANY
  address (8.8.8.8 via the DUT) gets the login page from the DUT's own MAC.
  `intercept-port <n>` and `intercept-port any` add ports (T33366).
- `auth-web-server intercept-port any` and `... 8080` are BOTH kept in running-config;
  `show auth-web-server` then prints only `any`. Remove each line separately.
- Once authorised, nothing is intercepted: the client's traffic to an unrouted address gets
  ICMP net-unreachable from the SVI. The host reports that as `Errno 101 Network is
  unreachable`, which looks like a host-side failure. Capture before grading it.
- `GET /` on the web-auth address returns the login page directly (200). Both a wrong and a right
  password return 200 with a refresh to `index.cgi?authenticating=1`, so **grade the login on
  `show auth supplicant brief` and the dataplane, never on the HTTP body.**
- **Web-auth DHCP server (T44276, 2026-10-29):** needs `service dhcp-server` (off in the bench baseline);
  without it `show auth-web-server` still says `DHCP server: enabled` and nothing is ever OFFERed.
  `auth-web-server dhcp ipaddress` equal to the host address is refused (`% Server address is already
  configured as host address, delete it first`); remove `auth-web-server ipaddress` and use a separate
  subnet (192.168.60.1/24 worked; 192.168.50.254/24 inside vlan1's subnet got no OFFER). Default lease 20 s
  (the AAA guide says 30), T1 10 / T2 12 whatever the lease; addresses go up by one per DISCOVER; a MAC's
  first DISCOVER is not answered. The login page is then served only to clients in the DHCP subnet.
- No `clear auth` command exists (`% Unrecognized command`). `dot1x initialize interface <port>`
  ends web and MAC sessions too.

### 1.2 Method changes and existing sessions
- Applying `auth-mac enable` to a port ended an existing **web** session on it (log: `Supplicant
  ckweb unauthorized`), and MSTP re-announced the port forwarding. If that client's MAC is in the
  RADIUS table, its next frame MAC-authenticates it (Mode M) and the first frame is lost.
- `no auth-web-server ssl` ended the web session on the port.
- `auth-web enable` adds `auth forward arp|dhcp|dns` (as on x960), so use ICMP for the dataplane check.

### 1.3 PKI (T33365, T33357)
- `crypto key generate rsa label <name> 2048`; zeroize is `crypto key zeroize <NAME>|all`.
  `crypto key zeroize rsa <name>` is `% Invalid input`.
- 🔴 **Entering `crypto pki trustpoint <name>` CREATES it** (`Created trustpoint`), including when
  it is used as a `qmark --mode`. Remove with `no crypto pki trustpoint <name>` (y/n). Same as
  x960 §7E.8.
- `subject` in the trustpoint is stored as `subject-name`. `subject-alt-name` exists; without it a
  CN-only server cert fails any client's hostname check for an IP URL.
- `crypto pki authenticate <tp>` and `enroll <tp>` ask nothing. Enroll for an RSA trustpoint
  also makes an ECDSA server cert, using the existing `server-default-ecdsa` key.
- Export order is `crypto pki export <tp> pem terminal rsa|ecdsa` (not `pem rsa terminal`).
- `crypto pki enroll local user <u>` asks for the export passphrase twice (ckcon `@ask`), as on
  x960. It is removed with `no crypto pki enroll local user <u>` ("Removed 1 PKCS#12 file").
- 🔴 **The PKCS#12 TFTP export to a client behind a `dot1x port-control auto` port that is still
  Unauthorized fails with `% Network is unreachable`** after a long silent "Copying...". The
  client's replies are blocked at ingress. Export before enabling dot1x, or force-authorise that MAC for the
  copy only (`auth supplicant-mac <mac> port-control force-authorized`, then `no ...`).

### 1.4 EAP-TLS (local RADIUS)
- With a DUT-issued client cert and the supplicant at TLS 1.2: EAP-Success at 1.06 s, the DUT's
  flight is 2367 B in 3 fragments and the client's is 2175 B in 2. A cert from another CA gets
  EAP-Failure. The authenticator offers MD5-Challenge before TLS.
- With wpa_supplicant 2.6 at default TLS (1.3), it stalls for 30 s and then gets EAP-Failure, the
  same as x960 §7K.3. That is the supplicant, not the DUT ([[eap-tls-needs-tls12-supplicant]]).
