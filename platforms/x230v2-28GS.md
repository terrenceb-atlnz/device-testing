# x230v2-28GS — platform facts (AT-x230-28GS V2)

**What this is.** The x230v2-28GS facts that cost the 2026-10-09 campaign time, or would have been
mistaken for a defect. Read it whenever the DUT is an x230v2 (`/orient-dt` §2). Unless a row says
otherwise, everything here was measured on **tb470 u0** (S/N A10783G262900002), build
**awplus_main-20261008-57**, bootloader **6.2.40**, campaign
[tb470/x230v2-28GS/CAMPAIGN-QUEUE-2026-10-09T0845.md](../tb470/x230v2-28GS/CAMPAIGN-QUEUE-2026-10-09T0845.md).
What the bench *currently* is lives in the box's generated `bench-state.md`, never here. How to add
to this file: [README.md](README.md).

Earlier x230v2 work (the 5700 bootloader 6.2.40 suite, burn-in) is in
[tb470/x230v2-28GS/](../tb470/x230v2-28GS/) and memory `x230v2-5700-control-corpus`.

## 1. Boot, config and builds

- **The x230v2-28GS is x220 hardware** with minor upgrades and a sales rebrand (Terrence,
  2026-10-13), so x220/x230 naming is inconsistent in the build, the CLI and the documentation alike.
  Treat an x220 name on this unit as expected, not as a defect or a wrong image.
- **The build name says x220.** `show version` reads `Build name : x220-awplus_main-…`; the
  release file is `x230v2_28GS-awplus_main-….rel`. Every x230v2 log has the same, so it is the build
  target name, not a wrong image (T47226, 2026-10-09).
- **`flash:/default.cfg` cannot be copied over or deleted from the CLI** (observed 2026-10-09,
  T47115). Every route was refused:
  - `copy <file> flash:/default.cfg` → `% Cannot overwrite flash:/default.cfg as it is configured as
    the boot config file`;
  - the same with the boot pointer moved away → `… as it is the default config file`;
  - `copy <file> startup-config` and `delete flash:/default.cfg` → refused the same way.
  - **`write` does update it.** So "back up default.cfg, change things, copy the backup back" does
    not work. Restore a test's startup change by making the running-config equal the original and
    `write` (not byte-identical: the header changes, and `service password-encryption` is not in
    running-config on this build so it drops out). A byte-exact restore would need `start-shell` +
    `cp` (not tried).
  - **The way round it (2026-10-12, tb470 u0):** give the unit its own boot config.
    `copy running-config flash:/<name>.cfg` then `boot config-file flash:/<name>.cfg`; `show boot`
    reads `Current boot config: flash:/<name>.cfg (file exists)` and `Default boot config:
    flash:/default.cfg` stays as the fallback. A reload then loads `<name>.cfg` (verified, 166 s).
    Which file tb470's x230 boots now is a bench fact: bench-state.md / the handover.
  - **`service password-encryption` is obsolete** on this build: config mode answers `The command
    'service password-encryption' has been obsoleted.` / `% Password encryption is already always
    enabled; no change made.` (2026-10-12). Its absence from a rewritten config is not a difference.
  - `no boot config-file` puts the pointer back to `flash:/default.cfg`; the next boot then prints
    `Loading default configuration` instead of `Loading configuration file flash:/default.cfg`, but
    did load the file (manager login and config intact, 20:29).
- **A boot updates `default.cfg`'s file date without any `write`** (2026-10-09: dated 18:35:16 after
  a reload, header still "saved on Thu Oct 8"). A changed mtime is not evidence of a save.
- **Reload time** ≈ 163–168 s to the login prompt; a **secure-mode boot ≈ 265 s** (TPM2 and FIPS
  start jobs). Allow for it in `@poll`/waits.
- **Each reload drops running-only config**, including `lldp run` that `bench_probe.py run` sets.
  Re-apply after every reload, or save it into the unit's own boot config (above).

## 2. Platform-facts table

| Fact (measured 2026-10-09, tb470 u0) | Consequence |
| --- | --- |
| No eth0 (`% Can't find interface eth0`) | Cases with an eth0 step: that step is N/A (T31855) |
| All 28 ports are SFP cages; no fixed copper | Auto MDI/MDI-X cases are UNSUPPORTED: an SFP is a pluggable transceiver, not a fixed copper port (Terrence, 2026-09-29, reaffirmed 2026-10-13; T33234). Copper SFPs keep their copper identity for speed/duplex/media in every other test |
| Copper SFPs (AT-SPTX/SPTXa/SPTXc) **refuse forced polarity**: `polarity mdi` / `polarity mdix` -> `% Polarity set failed port1.0.N`, log `EXFX: … Polarity mode not supported on this interface`; only `polarity auto` is accepted, and the port always reports `current polarity auto`. Auto MDI-X works on straight and crossover leads (2026-10-13) | Supporting evidence for T33234 UNSUPPORTED; the far end forcing `mdi` alone does not take the link down Docs (2026-10-13): the `polarity` command page and the Switching Feature Overview Guide (C613-22037-00 REV E, "MDI/MDIX connection modes") cover copper ports "on the switch" and say nothing about copper SFPs; framework suite 5703 (test-5000.1003) treats copper-SFP polarity as platform-dependent |
| `duplex half` after `speed auto 1000` -> `% Cannot set speed 1000 and half duplex port1.0.N`; `speed auto 100` + `duplex half` is accepted (2026-10-13) | library_5000 recognises the refusal ("Cannot") |
| RESTCONF (2026-10-13): `service restconf` is `% Unrecognized command` (on with `service http` alone); root `/restconf`, `/.well-known/host-meta` 404; interface disable/enable works by PUT on the `enabled` leaf, PATCH answers 204 and does nothing; no VLAN-database model (create 204 with no effect, delete 403) | Details: memory `awplus-restconf-api-reference`; T47228 FAIL |
| `show platform full-debug` lists `tpm2-abrmd --tcti=mssim` talking to `/usr/bin/tpm_server` on localhost:2321 (2026-10-13) | Expected: it is how the unit talks to the idevid servers (Terrence, 2026-10-13); not a fault (T45543) |
| No multicast routing: `ip multicast`, `ip mroute`, `ipv6 multicast` → `% Unrecognized command` | Static-mroute cases UNSUPPORTED (T30403) |
| `platform bist` and `platform prbs` are offered by the parser but refuse at run time (`% BIST test not supported.`, `% PRBS not supported on this platform`); prbs offers only `internal-fabric\|all-fabric` | T31863, T31866 UNSUPPORTED |
| **1000BASE-SX module accepts `speed 100` / `speed auto 100`**, reports `connected a-full 100`, passes no frames (partner stays at 1000, LLDP lost). Rejects 10/2500/10000/half correctly. The IE520 does the same | **Defect**, T47209 FAIL; probably shared AW+ code |
| Fixed `speed 1000` advertises autoneg "Disabled" in the LLDP MAC/PHY TLV while the link negotiates 1000/full | Noted at T47210, not graded as a fault |
| `crypto secure-mode` / `no crypto secure-mode` ask no (y/n); print `% Save the config and restart the system…`; `show secure-mode` reports the new setting before the reload | Needs `write` + reload each way |
| The secure-mode boot logs `user.warning … Verification of the release file has failed, please verify it.` and the banner asks for `crypto verify`; only that boot, not plain boots | Dev builds have no Download Center SHA256, so `crypto verify` does not apply; a failing saved pair would stop a secure-mode boot, so it was not tried |
| `no security-password minimum-categories` is rejected; set `minimum-categories 1` | Restore recipe |
| `no exec-timeout` under `line con 0` is accepted but leaves `exec-timeout 0 0`; a reload clears it | Possible defect, not graded (T31863) |
| Copper SPTX facing an IE520 AT-SPTXa cannot be driven at 10 Mb/s (the IE520 module rejects 10) | 10 Mb/s on the x230 SPTX is NOT MEASURABLE on tb470 (T47208) |
| The IE520 stack (STP off) does not forward BPDUs | STP loop cases need a direct x230 port-to-port lead or a hub (T20358 PARTIAL) |
| **`show cpu` prints busy averages (1 s / 20 s / 60 s), not an idle figure** (observed 2026-10-21, awplus_main-20261019-75, T46810/T28218 health reads) | A HEALTH line must say "busy n%"; do not read the first figure as idle |
